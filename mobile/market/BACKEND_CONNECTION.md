# Подключение мобильного Market к backend

Рабочий стек: React Native / Expo / TypeScript. Настройка и клиентские проверки ниже не подтверждают live/device-приёмку. До понедельника 2 ноября 2026 года серверные, денежные и provider-операции не выполняем.

## Адрес окружения

Получить у Никиты доступный устройству HTTPS-адрес API с доверенным сертификатом. В текущем backend `apps/api/src/bootstrap.ts` устанавливает префикс `api`: например, `https://<выданный-домен>/api`. `localhost` на телефоне относится к самому телефону. HTTP, пароль в URL, query и fragment текущий клиент не принимает.

Можно ввести адрес на первом экране приложения либо локально скопировать `.env.example` в `.env.local` и заменить пример значением `EXPO_PUBLIC_MARKET_API_URL`. Значение попадает в публичный bundle; паролей, access/refresh/CSRF-токенов и сервисных ключей в нём быть не должно. Изменение переменной окружения требует перезапуска уже разрешённого локального Expo-процесса. Автоматической смены сервера после входа нет.

При недоступном сервере дождаться ограниченного сетевого запроса, затем выбрать «Изменить адрес сервера». Старый адрес доступен для исправления. Язык сохраняется, локальная форма предыдущего подключения удаляется. При полученных credentials сначала применяется существующий сценарий выхода. Ошибочный начальный URL показывается сразу, до сетевого запроса.


Запуск Metro после подключения разрешённого окружения, если он понадобится отдельно:

```sh

```

Команда здесь документирована, в текущем срезе не запускалась. Старый APK не пересобран и не соответствует всем новым исходникам. Четвёртая попытка iOS, тяжёлые сборки, новые credentials/права и публикация не выполняются. Идентификаторы приложения остаются существующими.

## Проверка подключения после открытия live-окна

1. Проверить адрес, TLS и префикс `/api`. Не добавлять development identity headers. Первый запрос клиента — `GET /api/auth/current?workspace=BUYER`, с cookies и без Bearer.
2. При отсутствии cookie-сеанса показать вход. Существующий flow: `POST /auth/login` → `GET /identity/mfa` → при необходимости `POST /identity/mfa/challenge` → `GET /auth/workspaces` → явный выбор BUYER-организации → handoff/exchange → независимый `GET /auth/workspace-context`. Все пути относительны настроенному `/api`.
3. Проверить имя/организацию и исходные GET-сценарии, затем 401/refresh, 403, 429, сетевую ошибку и неверный JSON. Ответ сервера проходит существующие схемы; ошибка контракта не открывает доступ. Не повторять business POST автоматически.
4. Проверить подтверждённый `POST /auth/session-logout`, повторный вход и возврат из background. При смене actor/org/session старые данные и локальные формы должны исчезнуть.
5. Отдельно зафиксировать device/cookie-поведение. Backend устанавливает `mp_refresh[_buyer]` как HttpOnly, с путём `/api/auth`; CSRF-cookie имеет путь `/`. Нативный cookie jar принадлежит Expo transport. Refresh secret в JSON не допускается. Внешний reverse proxy должен сохранять существующие cookie/TLS-свойства.

Native BUYER создание и изменение подтверждённого отзыва подключены к существующим POST/PATCH и установленному Expo UUID-v4 API; неизвестный исход допускает только явный повтор исходного запроса. PATCH использует версию и не повторяется после неизвестного исхода; отдельное чтение опубликованной версии не доказывает отмену. Native ORDER/OFFER список и чтение переписки подключены к существующим GET; просмотр не отправляет отметку прочтения. Native комментарии заказа подключены к source POST/PATCH; creation сохраняет исходный ключ/текст, правка использует прочитанную версию и отдельное чтение после неизвестного исхода. Native ORDER/OFFER первое и последующие текстовые сообщения подключены к существующим POST; исходный запрос повторяется только явно с тем же ключом/текстом. Native личная отметка прочтения, завершение обычного диалога и обращение к оператору подключены только к явным действиям пользователя. Покупателю не выдаётся завершение рассмотрения поддержки. Native создание закупочного списка и сохранение/удаление позиции подключены к существующим keyless POST/DELETE. Неизвестные попытки не повторяются автоматически и сохраняются отдельно от текущего чтения. Native корзина: create/recover/add/PATCH quantity/DELETE item/validate/reprice/checkout подключены к существующим API. Только checkout требует SDK UUID; повтор неизвестного оформления явный, с исходными cart/version/key. Native поддержка: создание собственного общего обращения и публичный текстовый ответ подключены; ответ из ORDER/OFFER-диалога требует независимого чтения обращения и проверки связи. Неизвестный ответ сохраняет исходный текст и UUID для явного повтора. Native действия покупателя по заказу подключены к существующему workflow POST: отмена, приёмка, заявки на возврат, отметки отправки возврата и получения денег, повторная закупка, первоначальное согласование неоплаченного состава и спор по переводу. Доступность проверяется существующими моделями; сервер окончательно проверяет права и условия. Исходные версия и UUID сохраняются для явного повтора. Native чтение опубликованных отзывов по товару/поставщику подключено к существующим GET с исходными окнами100/200. Чужие варианты/поставщики и скрытые строки не принимаются. Переход к товару не отправляет запрос отзывов сам. Native поиск собственных опубликованных отзывов по текущему заказу готов: только текущий пользователь, купленный вариант/поставщик и окно200. Выбор открывает существующее изменение по версии без CREATE/UUID. Пустое окно не доказывает отсутствие остальных отзывов. Native GET счетов по заказу подключён в разделе «Документы»: подтверждённая история формирования, выбранный снимок и точные реквизиты/суммы. Изменение версии/ссылки счёта требует свежего чтения перед реквизитами. Загруженный текущий счёт может не иметь строки в этой истории. Остальные legacy business writer/key providers и проверка на устройстве остаются отдельной границей. Локально написанный flow и исходный API-контракт учитываются как клиентский код; успешная имитация транспорта не означает приёмку конкретного развёрнутого backend, разрешений, платежа или устройства.

Вопросы к Никите для подключения: точный HTTPS URL/префикс и TLS, доступная BUYER-организация/существующий способ выдачи тестового доступа, версия backend и соответствие session/cookie/response контрактам. Новые пароли или токены в этот документ не записываются.

Локально подключено заявление о ручном переводе с существующей квитанцией: «Заявленные переводы» → прочитать счёт/квитанции → выбрать → дата/время устройства и подтверждение факта → просмотр → отправка. REPORT_TRANSFER регистрирует заявление, поступление денег проверяется отдельно. Потерянный ответ допускает только явный повтор исходной попытки; отдельное чтение заказа сохраняет неизвестный исход. Новая загрузка файла и продуктовый payer-контракт этим срезом не принимаются.

Изображения PNG/JPEG в существующих сообщениях поддержки и диалогов заказа/предложения открываются по явному нажатию «Посмотреть изображение». Используется авторизованный бинарный GET: исходные размер/тип и сигнатура проверяются до показа. Смена родительского чтения и logout очищают выбранное изображение; повтор загрузки явный. PDF/офисные файлы остаются в метаданных, сохранение/отправка/новая загрузка требуют отдельного файлового пути.

После подтверждённого отзыва можно явно начать отзыв о другом предмете: поставщике или купленном варианте товара. Сохранённые отзывы открываются отдельно и используют свою последнюю сохранённую/явно принятую версию. Неизвестный CREATE сохраняет исходную попытку; неизвестный PATCH проверяется отдельным published-чтением, а история неизвестного результата остаётся у исходного ID отзыва.

На экране входа доступны регистрация email и запрос инструкции восстановления. Используются существующие анонимные POST, без cookies/Bearer и автоматического повтора. Ответ регистрации означает необходимость подтвердить адрес, ответ восстановления не подтверждает наличие учётной записи или доставку письма. В LOCAL_FILE-окружении инструкции обрабатывает оператор; ссылки/токены/пути файлов приложение не получает. Пароли очищаются при отправке; подтверждение адреса/сброс по почтовой ссылке и полное оформление компании остаются отдельными сценариями.

В заголовке сессии доступен «Двухэтапный вход»: явное чтение, ручное добавление ключа в аутентификатор, резервные коды и подтверждение; новая PENDING-настройка заменяет старые ключ/коды только после явного согласия. Подтверждение обновляет токен внутри прежней сессии, сохраняя бизнес-черновики/неизвестные попытки. Ответ401 может прийти после активации фактора: приложение не повторяет POST, а предлагает отдельное чтение. Отключение по коду завершает все сеансы по исходному API; после подтверждённого ответа очищается локальная сессия. Секреты остаются только в памяти текущего scope, QR/новые SDK/реальные настройки/устройства не запускались.

В настройках двухэтапного входа активной учётной записи доступна проверка текущего сеанса кодом аутентификатора или одноразовым резервным кодом. Новый токен применяется приватно, без сброса бизнес-черновиков и исходных неизвестных попыток. Ответ401 может прийти после расходования резервного кода: автоматического повтора нет; отдельное чтение и принятие текущего состояния сохраняет историю неопределённости. При потерянном ответе отдельный список показывает наличие/отсутствие строки, но не подтверждает исходное действие; принятие сохраняет историю неопределённости.
