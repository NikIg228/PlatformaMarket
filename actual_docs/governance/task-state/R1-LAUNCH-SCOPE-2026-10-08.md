## Сверка trust08.10 — что реализовано и чего не хватает

Срез main3012394, runtime1e666ee. Метод: статическое чтение схем/сервиса/engine,
поиск callers и consumers, проверка существующего exact-SHA CI evidence.

### Текущая формула надёжности поставщика0–100

| Показатель в engine | Вес |
| --- | ---: |
| Точность остатков |20% |
| Совпадение цены с заказом |15% |
| Полнота исполнения заказа |20% |
| Скорость подтверждения |10% |
| Доставка в срок |10% |
| Качество документов |10% |
| Качество коммуникации |5% |
| Свежесть данных |5% |
| Разрешение споров |5% |

Сумма весов100%. [Engine](../../../apps/api/src/modules/trust-commerce/trust-score.engine.ts)
получает события с metricCode, value0–1, собственным весом и временем; формула
не извлекает эти факты из заказов сама. Используется окно180 дней, влияние события
уменьшается вдвое каждые90 дней. Оспоренные/исключённые события не участвуют.
Менее5 пригодных событий → INSUFFICIENT_DATA, score=null; это **5 событий, не
5 заказов**. Каждая компонента сглаживается исходным значением0.78 с весом3:
`(0.78 * 3 + сумма(value * eventWeight * decay)) / (3 + сумма(eventWeight * decay))`.
Итог —100 × сумма(component × weight). Отдельно хранится confidence
`1 - exp(-eventCount/12)`, сильные/слабые стороны и рекомендации по улучшению.
При отсутствии событий конкретной категории компонент остаётся на исходной
оценке; это текущая техническая эвристика, не доказанная бизнес-методика.

### Отзывы1–5 — отдельная сущность

[Схема](../../../packages/schemas/src/trust-commerce.ts) содержит общую оценку и
7 отдельных оценок1–5: наличие, цена, подтверждение, комплектность, доставка,
документы, коммуникация. В [сервисе](../../../apps/api/src/modules/trust-commerce/trust-commerce.service.ts)
отзыв создаёт клиника-участник по своему заказу; варианты товара проверяются
по строкам заказа. Допустимые текущие статусы: DELIVERED, PARTIALLY_FULFILLED,
RETURN_DISPUTE, REJECTED, CANCELLED — не только успешно завершённые покупки.
Есть уникальность отзыва на заказ/организацию/цель, идемпотентный повтор,
редактирование с версиями/историей, ответ поставщика, moderation и appeal/audit.
Подозрение на персональные данные или всплеск отзывов отправляет отзыв в PENDING.
Рейтинг0–100 не является средним звёзд: пересчёт читает только metric events;
отзывы учитываются отдельно как reviewCount, автоматический перевод их оценок
в события рейтинга в просмотренном коде отсутствует.

## Форма отзыва клиники о поставщике — проектирование R7.5

Уточнение владельца08.10: предусмотреть компоненты и поля отзыва в roadmap,
затем продолжить R1. Исходный main eb4010b чистый; владелец scope прежний,
product primary idle. Изменение только документационное. Риск — заставить
клинику оценить неоказанную услугу или выдать проект формы за готовый UI.
Проверки этого шага: схема полей, shared controls, ссылки, согласованность и diff;
app/DB/browser gates не требуются до реализации.

Вход в форму — действие «Оставить отзыв» в доступном клинике заказе.
Поставщик и заказ определяются сервером и показаны как неизменяемый контекст.
Если отзыв уже есть, показываются он и доступное действие редактирования,
а не вторая форма создания. Причина недоступности действия объясняется.

| Поле/компонент | Предлагаемое поведение и существующая граница |
| --- | --- |
| Общая оценка | Обязательный выбор1–5, без выбранного значения по умолчанию; у каждой оценки понятная текстовая подпись |
| Оценки по критериям | Наличие, цена, скорость подтверждения, комплектность, доставка, документы, общение; шкала1–5 отдельно для каждого критерия |
| Комментарий | Необязательный многострочный текст до4000 символов после trim, счётчик и ошибка у поля; подсказка не указывать персональные/платёжные данные |
| Товар | Необязательная связь только с вариантом из этого заказа; основной адресат отзыва — поставщик |
| Отправка | Ясное действие «Отправить отзыв», защита повторного нажатия; результат различает опубликованный отзыв и отправленный на модерацию |
| Редактирование | Существующее окно14 дней, version conflict и история; введённый текст сохраняется при исправимой ошибке |

**Открытое продуктовое решение перед реализацией:** предложен ответ «Не могу
оценить / не применимо» для отдельных критериев. Текущий API требует все7
числовых оценок, хотя разрешает отзыв для CANCELLED/REJECTED. Нельзя подставлять
пятёрку, ноль или общий балл за доставку/документы, которых не было. Сначала
согласовать применимость критериев по фактам заказа и влияние пропуска на
агрегацию, затем связно изменить Zod/API/client/UI и regression tests.
Общая оценка остаётся отдельной от автоматического trust score.

Композиция использует shared field/textarea/button adapters и tokens из
[дизайн-системы](../../ui-ux/DESIGN_SYSTEM.md). Для шкалы оценок сначала проверить
общий доступный control; при отсутствии нужного варианта расширить shared adapter,
не создавать локальные стилизованные звёзды. Нужны label, group semantics,
управление клавиатурой, видимый focus, ошибки около поля и мобильная раскладка.
До UI/reference — паспорт параметров и оба JSON-контракта по дизайн-системе.

DoD реализации: reachable apps/web flow и состояния loading/недоступно/пустая
форма/validation/submitting/опубликовано/модерация/error/retry/conflict; данные
не теряются при recoverable ошибке. Целевые проверки доказывают своё/чужое
заказное основание, допустимый lifecycle, duplicate/idempotency, ограничения
редактирования, клавиатуру и screenshot/computed styles. Ответ поставщика,
жалоба и операторская модерация остаются частями общего R7.5.
