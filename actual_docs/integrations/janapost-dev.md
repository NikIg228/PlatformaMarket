# JanaPost B2B Domestic — первый этап R5 / SHIP-01

На 26.11.2026: JanaPost указан в целевом сценарии R5. Полученная документация
B2B Domestic Partner API v1.4 описывает DEV API. Первый этап добавляет внутренний
серверный адаптер чтения. Готовность сценария поставщика и подключение в корзине
оцениваются отдельно по [SHIP-01](../MAIN_ROADMAP_TO_PRODUCTION_2026-10-06.md#ship-01).

Адаптер отправляет пять типов данных: родительский идентификатор для справочника,
район, адрес и пагинацию для поиска отделений, трек-номер для проверки статуса.
Справочник адресов публичный. Поиск отделений и проверка статуса используют DEV
и подпись HMAC-SHA256 от канонического JSON. Ответы поиска отделений и справочника
пока остаются внутренними данными провайдера. Для статуса адаптер проверяет поле
`status` и возвращает значение без изменения состояния заказа.

Адаптер ещё не зарегистрирован в модуле логистики. Для внутреннего вызова
используются `JANAPOST_DEV_ENABLED`, `JANAPOST_DEV_CLIENT_ID`,
`JANAPOST_DEV_SECRET`. Production и limited stand блокируются. Timestamp
уникален в рамках экземпляра адаптера. Перед работой с одним credential из
нескольких процессов требуется подтвердить окно допуска и согласовать выдачу
timestamp. Секреты и реальные данные в фикстуры не входят.

Проверка этапа: изолированный тест на заглушках транспорта, типы и сборка API,
проверка diff. Перед подключением кабинета поставщика необходимо подтвердить
фактические формы ответов поиска отделений и статуса, в том числе envelope ошибок.

Следующий участок — выдача трек-номера, поиск или создание получателя, создание
отправления и этикетка. До включения записи нужно уточнить схему `clientInfo`,
результат повторного создания по тому же `mailNo` и способ сверки при таймауте.
Тариф, срок, схема нескольких отправителей, отмена и возврат остаются в
[условиях доставки](../OPEN_QUESTIONS.md#v13). Для кабинета нужны привязка к
организации и заказу, проверка прав и отображение состояний, включая восстановление
после неоднозначного ответа.

## Локальная панель в заказе поставщика

К внутреннему адаптеру чтения добавлен независимый сценарий на синтетических
данных. В карточке заказа поставщика с правом `delivery.view` панель позволяет
выбрать город, получить список демонстрационных ПВЗ, выбрать пункт и увидеть
пример статуса. Шымкент проверяет сценарий пустого списка. API проверяет,
что заказ принадлежит организации поставщика. Выбор пункта хранится в панели
до смены города или повторного поиска. Записей в заказе и запросов к JanaPost нет.

Для разработки запустить существующий `npm run dev:local` с переменными
`JANAPOST_LOCAL_FIXTURES=true` и `NEXT_PUBLIC_JANAPOST_LOCAL_FIXTURES=true`.
Маршрут выключен по умолчанию, в production и на limited stand. DEV-ключи
для этого сценария не требуются.

26.11.2026 проверено в Chrome на отдельной тестовой БД: доступ к своему заказу,
выбор пункта в Алматы и Астане, пустой список по Шымкенту, повторный поиск
с клавиатуры, тестовый статус и отображение на десктопе и при ширине 390 px.
Запрос без сессии получил HTTP 401. Временный вход поставщика отключён.
Рабочая локальная БД не обновлялась, для запуска использована тестовая БД,
где уже была применена ожидающая миграция `20261123210000_yandex_delivery_attempts`.

## Покрытие сценария доставки

Сверка B2B Domestic Partner API v1.4 и двух коммерческих предложений с
[П28/П29](../MAIN_ROADMAP_TO_PRODUCTION_2026-10-06.md#delivery-common-carrier)
и [SHIP-01](../MAIN_ROADMAP_TO_PRODUCTION_2026-10-06.md#ship-01).

| Этап Market | Что есть в материалах JanaPost | Что проверить или подтвердить |
| --- | --- | --- |
| Доступность и выбор ПВЗ | Иерархия адресов и поиск отделений, условия до 20 кг и 50 × 35 × 35 см | Схема ответа DEV, доступность отделения для отправления, правила для нескольких мест и отправителей |
| Цена и срок до оплаты | Весовая сетка для склад → ПВЗ, доплата за дверь, отдельный тариф крупногабарита из Алматы, сроки с приёма перевозчиком | Округление, границы 20/21 кг, формула объёмного веса, НДС, забор, перемер и гарантия суммы, поддержка обеих услуг в API |
| Создание и этикетка | Выдача `mailNo`, поиск или создание клиента, создание отправления, PDF | Поля `clientInfo`, поиск факта создания по треку, повтор с тем же треком, создание нескольких отправлений одного заказа и повторная выдача этикетки |
| Трекинг и вручение | Запрос по треку и состояния перевозки, выдачи и возврата | Фактическая форма ответа, лимиты опроса, вебхуки, значение статусов потери/аннулирования. Вручение перевозчиком не меняет приёмку, документы или деньги Market автоматически |
| Отмена, смена получателя, возврат | Описан статус возврата | Операции, допустимые стадии, плательщик, адрес возврата, обмен подтверждениями |
| Общий перевозчик корзины и расчёты | Коммерческие предложения описывают отдельное отправление | Договорная схема нескольких поставщиков, суммирование доставки, разделение платежей, сверка начислений и возвратов |

Локально проверены HTTP-ошибки 401/429/503, повреждённый ответ и таймаут
транспорта. Запрос чтения не повторяется сам, а явный повтор подписывается
с новой отметкой времени. Контракт клиента проверен для маршрута заказа
и пустого списка ПВЗ. Эти проверки не подтверждают идемпотентность создания.

До получения ответов можно прогнать на заглушке жизненный цикл отправления:
успех, таймаут после принятия, временно отсутствующий трек, затем сверку,
повторную выдачу этикетки и отдельные статусы получения Market. В боевую
логику не переносить поведение заглушки как гарантию JanaPost. Первый
живой проход — три чтения на DEV с синтетическими данными и тестовым треком.
