# Единое приложение PlatformaMarket — план реализации

Дата: 28.09.2026. ID: UNIFIED-APPLICATION-PLAN-2026-09-28.
Статус: документирование согласованного направления; миграция не начата.
Актуальное решение владельца после анализа 28.09.2026: сохранить уточнения
в этом плане; сейчас продолжать текущий frontend. Миграция единого приложения
отложена до отдельного поручения. Уточнения и следующий шаг — в §9.
Основание: запрос владельца в боковом обсуждении — объединить публичный сайт
и кабинеты в одно приложение, один пользовательский адрес и запуск `npm run dev`.
Текущий scope: только этот документ. Он не разрешает переключение действующего
окружения, перенос кода, реализацию оплат или изменение данных.

## 2. Целевой результат и границы

Один Next.js frontend, условное имя `apps/web`, одна его сборка и единый origin:

| Область | Предлагаемый маршрут | Доступ |
| --- | --- | --- |
| Каталог и публичные страницы | `/`, `/catalog`, `/products/[id]`, `/about` | Публичный, без раскрытия закрытых условий |
| Вход и подключение | `/login`, `/register`, маршруты восстановления | По правилам подтверждения личности |
| Клиника | `/clinic/*` | Активное членство и разрешения клиники |
| Поставщик | `/supplier/*` | Активное членство и разрешения поставщика |
| Площадка | `/admin/*` | Серверные полномочия сотрудника площадки |
| API через общий адрес | `/api/*` | Проксирование к существующему NestJS API |

Точные соответствия старых и новых URL фиксируются инвентаризацией; существующие
ссылки не удаляются произвольно. Выбор маршрута не выдаёт роль или полномочия.

После подготовки зависимостей `npm run dev` запускает весь необходимый локальный
runtime и сообщает один адрес браузеру, например `http://localhost:3000`.
Порт 3000 — целевой пример, его доступность проверяется launcher. При конфликте
выводится понятная ошибка, чужой процесс не останавливается.
Браузер не должен обращаться к отдельным портам кабинетов или API.

Внутри остаются отдельные процессы web/API и необходимые workers. База данных,
очередь и хранилище остаются инфраструктурными зависимостями. Их настройка
описывается отдельно; одна команда не означает отсутствие этих зависимостей.
В production используется production-сборка и управляемый запуск, не dev-server.

Не переносить доменную логику из NestJS в страницы/Next handlers. Сохранить
schemas, api-client, Fluent UI, деньги в minor units, транзакции, резервы,
идемпотентность, аудит, продуктовые ограничения и существующие данные.
Не добавлять микросервисы, новую UI-библиотеку или платёжные интеграции.

## 3. Последовательность работ и результаты этапов

### Этап 0. Зафиксировать исходную версию и карту переноса

Начинать после согласования единственного исполнителя и состояния текущего WIP.
Собрать страницы всех четырёх приложений, layouts/providers, API proxies,
auth callbacks, cookies/storage, CSP, env, feature flags, CSS, public assets,
metadata, sitemap/robots, старые ссылки и тестовые fixtures.
Учесть ссылки из приглашений, писем и документов, загрузки файлов и уведомления.
Записать baseline запуска, сборки, bundle sizes и критических сценариев.

Результат: таблица «старый маршрут → новый маршрут → права → тест → обратимость»;
перечень переносимого поведения и известных исходных дефектов. Ошибки исходной
версии не скрывать и не считать автоматически частью этой миграции.

### Этап 1. Утвердить границы приложения и доступа

Оформить ADR, структуру модулей и матрицу разрешений. Общий layout содержит только
действительно общие зависимости; providers клиники, поставщика и оператора
подключаются в соответствующих областях. Не оборачивать весь сайт в gate клиники.
Общие components/hooks/utilities выносить без копирования доменных правил.
Сохранить отдельные loading/error/not-found состояния и доступность.

Результат: понятная структура, в которой перенос одного кабинета не меняет права
другого. Код кабинетов не включается целиком в начальный публичный bundle.
Разделение bundle — оптимизация; защиту данных обеспечивает сервер.

### Этап 2. Создать каркас и перенести публичные страницы

Перенести каталог, карточку, информационные страницы и публичные assets.
Сохранить актуальные API-данные, фильтры/сортировку в URL, возврат и загруженную
часть выдачи, изображения, metadata и canonical URL. Не делать попутный редизайн.
Разделить глобальные стили и локальные стили областей, устранить дубли providers.

Результат: публичный сценарий работает из новой сборки без зависимости от старых
web-процессов. Ошибка API отличается от пустой выдачи, приватные ответы не попадают
в публичный кэш или статическую генерацию.

### Этап 3. Единая авторизация и контекст организации

Перенести вход, регистрацию, восстановление, приглашения, выход и проверку
сессии. Backend подтверждает пользователя, активное членство и capabilities.
Разделить личность пользователя, выбранную организацию и текущую область UI.
При нескольких организациях показывать явное переключение; не выдавать доступ
только потому, что пользователь открыл `/supplier` или `/admin`.

Пересмотреть названия/path/domain cookies: прежние cookies отдельных кабинетов
не должны конфликтовать. Сохранить HttpOnly для refresh, Secure в production,
CSRF-защиту и server-side revocation. Не переносить токены в URL или открытые
хранилища ради упрощения переходов. Удаление handoff разрешается только после
переноса всех его потребителей и проверки старых входных ссылок.

При смене организации отменять старые запросы, игнорировать запоздалые ответы,
очищать/разделять private caches и запрещать отправку старой формы от новой
организации. Определить поведение нескольких вкладок, refresh и отзыва доступа.
Каждая операция проверяет tenant и permission на backend до чтения/записи.

Результат: вход и возврат работают в одном origin, а права не смешиваются.
Рекомендуемая стратегия cutover — повторный вход после переключения, если
безопасная совместимость старых сессий не доказана. Это решение нужно явно
включить в rollout и уведомление пользователей, не выполнять молча.

### Этап 4. Последовательно перенести кабинеты

Порядок: клиника → поставщик → оператор. Для каждой области: маршруты, меню,
forms, файлы, уведомления, права, API contracts, error states и критические тесты.
Сначала принять один кабинет, затем переносить следующий.

Переносить уже существующие функции, не достраивать отложенный продуктовый backlog.
Не менять правила оплаты, акций, заказов или комиссии под видом унификации.
Действия поддержки сохраняют permission checks и аудит; UI оператора не получает
прямой универсальный доступ к БД.

Результат: три кабинета используют общую инфраструктуру без четырёх frontend
сборок; бизнес-сценарии и полномочия не меняются.

### Этап 5. Единый запуск, сборка и развёртывание

Изменить launcher, npm/Turbo dependencies, env validation, CI, deployment config
и runbooks. Проверить каждую ссылку на старые имена apps и порты.
Launcher проверяет зависимости/readiness, сообщает отдельные ошибки web/API,
останавливает только собственные дочерние процессы и корректно завершает их.
Успешный старт страницы не выдаётся за готовность API/worker.

Общий `/api` proxy имеет фиксированный upstream; служебные порты не публикуются
в интернет. Согласовать HTTPS, trusted proxy headers, host/origin allowlists,
ограничения размера запросов, streaming/downloads и используемый transport
уведомлений. Не вводить новый transport ради миграции.

Сохранить согласование pilot/go_live и build-time профиля. Production secrets
не попадают в `NEXT_PUBLIC_*`, bundle, logs или source maps. Одна проверенная
сборка выпускается как единый web-артефакт вместе с совместимой версией API.

Результат: одна команда для локального старта и воспроизводимая процедура выпуска.
Измерить время cold/warm build и запуска; ускорение подтвердить числами baseline,
а не обещать заранее. API/worker остаются самостоятельными runtime-компонентами.

### Этап 6. Приёмка, переключение и удаление старых точек запуска

Проверить весь новый маршрут на изолированном окружении и совместимость API.
Сделать пробное переключение и откат. Старые приложения убирать из активной
сборки/launcher только после доказанной функциональной эквивалентности.
Временное сосуществование допускается для проверки миграции; итоговый runtime
не должен требовать запуска четырёх старых frontend-приложений.

Старые публичные GET-ссылки перенаправлять по явной карте; не перенаправлять
автоматически POST/PUT/DELETE и не повторять изменяющие запросы. Сохранить query
контекста каталога, отфильтровывая недопустимые returnTo и внешние destinations.

Результат: опубликованные evidence, актуальные ADR/runbook/acceptance status,
удалённые устаревшие зависимости запуска и проверенный rollback.

## 4. Реестр рисков и обязательные меры

Это модель рисков будущего изменения, не список доказанных уязвимостей кода.
Полноту нельзя гарантировать: реестр уточняется по фактическому diff и проверкам.

| Риск | Мера и проверяемое условие |
| --- | --- |
| Доступ к чужой организации, IDOR/BOLA | Tenant и permission проверяются сервером для объектов, списков, exports и файлов; прямые запросы с чужими ID отклоняются без утечки данных |
| Повышение полномочий через URL/role selector | Сервер не доверяет роли, tenant или actor из клиента; маршруты не назначают capabilities; approval не заменяет authorization |
| Смешение организаций при переключении | Tenant-aware private cache, блокировка устаревших mutations, отмена запросов и проверка поздних ответов; тесты нескольких вкладок |
| Утечка через SSR/RSC/CDN/prefetch | Публичные и приватные данные разделены; приватные ответы не кэшируются общим кэшем; тест двух пользователей на прогретом кэше |
| CSRF и конфликт cookies | Явная схема cookies и их очистки, проверка origin/CSRF на изменяющих операциях, Secure/HttpOnly по назначению; SameSite не единственная защита |
| Кража/фиксация сессии, гонки refresh | Ротация/отзыв по действующему контракту, координация refresh, проверка sessionId; выход и отзыв доступа проверяются сервером |
| XSS затрагивает все кабинеты одного origin | CSP/nonce сохраняются, пользовательский HTML и файлы не исполняются как доверенный код, опасные render paths проверяются; права API не ослабляются |
| Ложная изоляция `/admin` | URL-путь не изолирует браузерный origin. Операторские permissions, аудит и усиленная проверка критических действий обязательны; MFA/step-up — отдельное решение перед production |
| Open redirect и утечка токенов | Allowlist внутренних returnTo, запрет protocol-relative/external destinations, отсутствие секретов в URL/referrer/logs |
| SSRF/open proxy через `/api` или изображения | Фиксированные upstreams, существующие outbound policies, проверка redirects/URL; пользователь не задаёт произвольный внутренний host |
| Инъекции и mass assignment | Сохранить общие схемы и server validation, разрешённые поля/параметризованные запросы; унификация не расширяет принимаемые DTO |
| Опасные вложения/выгрузки | Проверить ownership, MIME/content-disposition, size limits, traversal и доступ по ссылкам; storage не становится публичным из-за общего origin |
| Повтор операций после timeout/переключения | Не повторять writes без поддержанной идемпотентности; сохранить transactional checks остатков и денег, revalidation checkout |
| Падение одной web-сборки затрагивает всех | Route error boundaries для UI, supervision/readiness для процесса; boundaries не защищают от падения процесса или exhaustion памяти |
| DoS через поиск/импорт/загрузки | Сохранить ограничения, rate limits и timeout budgets; тяжёлые задания не выполнять в web request; проверить ресурсы и деградацию |
| Смешанные версии при выпуске | Совместимость web/API, assets и контрактов, единый release identifier, пробный rolling update и возврат; не предполагать совместимость кешей |
| Включение скрытых функций профиля | Fail-safe pilot/default, согласованный backend/build profile, отрицательные проверки optional endpoints и UI |
| Утечка секретов и supply-chain проблемы | Проверка public env/bundles/logs, действующие dependency/security checks; не совмещать перенос с необоснованным обновлением стека |
| Потеря ссылок, SEO, accessibility | Карта URL, metadata/redirect tests, back/forward, focus/keyboard и mobile; не объединять конфликтующие global styles вслепую |

Отдельное ограничение: объединение с операторской панелью увеличивает общую зону
последствий XSS. Если оценка угроз требует отдельного origin для оператора,
пересмотреть именно это требование до production. Один репозиторий/артефакт
может сохраниться, но это уже исключение из цели одного пользовательского origin
и требует отдельного решения владельца. Не скрывать этот компромисс.

## 5. Устойчивость, наблюдаемость и откат

Единое приложение упрощает сопровождение, но само по себе не обеспечивает высокую
доступность. Для production согласовать нагрузку, доступность, RTO/RPO и бюджет.
При требовании переживать отказ экземпляра нужны резервирование, балансировка,
readiness, graceful shutdown и независимая устойчивость БД/очереди/хранилища.
Количество реплик определяется измерениями и целью, а не этим документом.

Сохранить requestId и аудит, добавить измерения ошибок по областям и ролям без
секретов/персональных данных в логах. Контролировать latency, 5xx, login failures,
ресурсы процессов, очередь и health зависимостей. Ошибку API показывать честно;
не подменять её фиктивными успешными данными каталога.

План отката для каждого переключения:

1. Сохранить предыдущие web/API артефакты и конфигурацию маршрутов; указать их версии.
2. До выпуска проверить восстановление маршрутизации и совместимость cookies.
3. При утечке tenant-данных, нарушении входа/прав или критических сценариев
   остановить rollout; пороги performance/error regressions задать до выпуска.
4. Вернуть предыдущую совместимую версию, выполнить smoke входа и трёх кабинетов.
5. При несовместимости сессий выполнить предусмотренный отзыв/повторный вход.
6. Не откатывать рабочую БД из backup поверх новых заказов ради отката UI.

Объединение frontend не требует массового переноса товарных/заказных данных.
Если обнаружится необходимая schema migration для сессий — отдельный контракт,
expand/contract, upgrade-path и проверка обратной совместимости до cutover.
Backup и доказанная restore-процедура нужны для эксплуатации, но не заменяют
совместимый rollback приложения.

## 6. Матрица приёмки реализации

| Область | Обязательное доказательство |
| --- | --- |
| Запуск | `npm run dev` из canonical root; один адрес; публичная часть и три кабинета без четырёх прежних web-процессов; ошибки зависимостей и занятый порт |
| Auth | Гость, clinic, supplier, operator, несколько организаций, приглашение, восстановление, истёкшая/отозванная сессия, refresh и несколько вкладок |
| Изоляция | Чужие ID и tenant, прямые API/URL, download/export, прогретый кэш, смена организации при запросе и отправке формы |
| Продукт | Каталог/карточка/корзина, существующие сценарии заказов, товары поставщика, импорт, операторские действия без изменений доменных правил |
| Навигация | Старые ссылки, безопасный returnTo, фильтры, сортировка, пагинация/загруженная часть, back/forward, images/downloads |
| UI | Desktop/mobile, keyboard/focus, loading/empty/error, меню и dropdowns, отсутствие конфликтов CSS и публичной загрузки всего admin UI |
| Сбои | API timeout/503, потеря сети, двойное нажатие, restart, незавершённые jobs, повторное подключение уведомлений по существующему контракту |
| Выпуск | Production build, profile consistency, compatible web/API, воспроизводимый артефакт, пробный rollout/rollback и фактический CI |

Для изменения TypeScript: `npm run typecheck`, `npm test`, `git diff --check`.
Для перенесённых critical UI flows: `npm run verify:web` и production build.
По фактически затронутым рискам Workflow: `verify:core-contract`,
`verify:postgres` для tenant/transaction изменений, `verify:runtime-split`,
`verify:production-config`, проверки frontend/pilot composition. Существующие
gates адаптируются к одному frontend, их требования не удаляются ради PASS.
Перед заявлением релизной готовности — соответствующий `verify:release`.

Fixtures с записью — только проверенная disposable test DB, никогда рабочий
demo-каталог. Зафиксировать входы, профиль, команды и результаты; соблюдать
лимит попыток Workflow. Платёжные deferred сценарии не возобновлять: если gate
упирается в них, фиксировать BLOCKED и отдельно определять разрешённую границу.

Для production необходим security review фактического diff и negative tests
указанных границ. Наличие этого документа не означает прохождение аудита.

## 7. Решения, которые ещё нужно уточнить

1. Окончательный домен и карта старых URL; срок поддержки старых входных ссылок.
2. Подтверждение размещения оператора в одном origin с публичной частью с учётом
   увеличения последствий XSS; требования MFA/повторного подтверждения действий.
3. Окно переключения и повторный вход либо доказанная совместимость старых сессий.
4. Хостинг, ожидаемая нагрузка, требуемая доступность и допустимые RTO/RPO.
5. Ресурсные бюджеты, численные пороги performance regression и условия отката.

Неопределённость этих пунктов не мешает инвентаризации и локальному каркасу,
но зависимые production-решения нельзя подменять неявными предположениями.

## 8. Статус документа и передача

Документ подготовлен в отдельном боковом обсуждении; владелец основного scope
каталога не изменён. Единственное разрешённое изменение — этот файл; код,
процессы, БД, registry, текущие checkpoints и чужой WIP не менялись.
Применены практики Agency Backend Architect: модульные границы, threat/risk
inventory, контрактная совместимость, наблюдаемость и обратимая миграция.
Полный security scan и runtime проверки в docs-only scope не выполняются.

Следующий шаг реализации: назначить единственного исполнителя после завершения
или явной приостановки текущего scope; выполнить этап 0 на актуальном снимке.
Публикацию этого документа согласовать с единственным writer при включении в
основную историю; этот боковой scope не коммитит и не публикует общий checkout.

## 9. Результаты анализа и уточнения перед реализацией — 28.09.2026

Дополнение основной задачи по прямому запросу владельца. Раздел 8 сохраняет
историю подготовки документа. Текущий scope — документирование анализа;
объединение приложений сейчас не начинается. Продолжается работа над текущим
frontend по отдельным конкретным задачам владельца.

### Вывод

Один Next.js frontend при сохранении NestJS API — подходящая архитектурная
основа. План учитывает контракты, tenant isolation, профили, старые ссылки и
обратимость. До реализации необходимы карта переноса, точная модель сессий и
критерии завершения этапов. Объединение само по себе не завершает функционал
пилота и не гарантирует ускорение сборки или запуска: нужны измерения.

### Наблюдения по текущему коду и необходимые уточнения

| Область | Наблюдение | Что определить до переноса |
| --- | --- | --- |
| Маршруты | Клиника и поставщик имеют `/orders/[id]` и `/documents`; ссылки в компонентах заказов ведут на `/orders/...` | Полную карту старых и новых URL, включая письма и документы; единые функции построения ссылок с областью кабинета |
| Сессии | Общий workspace-клиент использует контекст BUYER/SUPPLIER, refresh и серверную проверку членства | Выбрать одну пользовательскую сессию с контекстом организации либо несколько сессий кабинетов; определить logout, refresh, несколько вкладок и переключение организации |
| Оператор | `apps/admin-web/app/admin-auth.ts` отдельно обрабатывает sessionStorage, `#session=` и локальный fallback identity headers | Явно спроектировать подключение оператора к общей авторизации; не переносить локальный fallback как штатный доступ. Расхождение кода не доказывает обход серверной защиты |
| Layout/providers | Buyer root layout включает `OrganizationGate`, `SupplierCatalogSession` и `DeliveryProvider` | Отдельные оболочки публичной части и кабинетов; общий корень не должен навязывать клинический gate всему сайту |
| Production API | В прочитанном buyer Next config rewrite `/api` включён только в development | Выбрать production proxy и его конфигурацию: fixed upstream, cookies, uploads/downloads, timeouts и доверенные заголовки; локальная работа не доказывает production readiness |
| Перенос исходников | План не выбирает физический способ переноса feature-модулей | Переносить существующие компоненты без дублирования и переписывания бизнес-правил; временные импорты из старых apps допускаются только с явным условием их устранения |
| Приёмка | Есть общая матрица, но нет точных сценариев каждого кабинета | Для каждого этапа указать fixtures, команды, ожидаемые результаты, известные исходные дефекты и критерий перехода дальше |

Рекомендация по сессиям: единая подтверждённая личность пользователя, отдельно
выбранная организация и область интерфейса. Это рекомендация для будущего ADR,
а не уже принятое изменение серверного контракта. Если понадобятся изменения
сессий/API, выделить их в самостоятельный проверяемый этап по общему маршруту
контракт → backend → клиент → UI.

### Оператор и общий origin

`/admin` не создаёт браузерной изоляции. Один frontend-артефакт и один origin —
отдельные решения. Единый адрес удобен для локального стенда; перед production
нужно явно принять размещение оператора и требования усиленной проверки
критических действий с учётом общей зоны последствий XSS. Не считать этот
анализ полноценным security audit или подтверждением production-безопасности.

### Рекомендуемый порядок после отдельного возобновления миграции

1. Зафиксировать текущий WIP и ограничения проверок на актуальном снимке.
2. Составить карту маршрутов, ссылок, assets и providers всех приложений.
3. Принять ADR с моделью сессий, контекстом организации, операторским доступом
   и конкретной production-схемой проксирования.
4. Создать каркас и перенести каталог и карточку без попутного редизайна.
5. Перенести авторизацию, затем клинику, поставщика и оператора; принимать
   каждый кабинет отдельно до следующего переноса.
6. Переключить основной launcher только после проверки нового приложения
   без старых frontend-процессов.
7. Проверить откат, затем убрать старые приложения из активной сборки.

Незавершённые проверки каталога и отложенные платёжные сценарии остаются
отдельными пунктами со своими статусами и счётчиками попыток. Миграция не
исправляет их автоматически, не сбрасывает ограничения и не разрешает
возобновлять оплаты. До следующего явного поручения миграция отложена.

Анализ выполнен чтением плана, launcher, маршрутов, auth-кода, buyer layout/
Next config и ADR 010/014. Применены практики Agency Backend Architect:
границы компонентов, совместимость и обратимость. Runtime/security suites
для этого документального дополнения не запускались; код и данные не менялись.
