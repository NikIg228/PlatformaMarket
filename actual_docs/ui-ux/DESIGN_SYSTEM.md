## Обязательное переиспользование вместо локальных вариантов

Уточнение владельца07.10.2026: этот документ и указанные в нём JSON — единый
источник правил и значений для текущих и последующих UI-задач и референсов.
Стандартные кнопки, поля, селекторы, карточки и состояния собираются из
существующих shared adapters/variants и tokens. Нельзя создавать их локальные
копии или переопределять геометрию, типографику, цвета, focus и selected/hover
через CSS modules, inline styles, селекторы Fluent или произвольные значения.
Использование token само по себе не разрешает локально менять shared control.

Feature-компоненты для бизнес-сценариев допустимы: они компонуют общие примитивы,
а не вводят собственную дизайн-систему. Локальный CSS отвечает за композицию
(сетка, колонки, ширина, размещение, responsive reflow); применимые отступы,
цвета и типографика в нём также берутся из общих tokens и принятой иерархии.

Если подходящего варианта нет, сначала проверить существующие consumers и API.
Нужное расширение делать в shared adapter/контракте в рамках разрешённой задачи,
с проверкой затронутых consumers. Новые общие параметры или исключения не
вводятся молча: требуется явное основание в запросе владельца и запись решения.
Старые локальные отклонения не являются образцом и не разрешают массовую
чистку вне scope. При review проверять не только валидность token, но и отсутствие
локального дублирования и overrides; static guard не заменяет эту проверку.

## Использование

Базовые контролы импортировать из `@marketplace/ui/controls` или общего barrel.
Внутри packages/ui — из `./controls`, чтобы не создавать циклы через barrel.
Прямой импорт Button/Input/Textarea/Select/Field/Checkbox/Dropdown/Combobox из
Fluent запрещён ESLint вне адаптера. Другие Fluent primitives сохраняются.

```tsx
<DmButton appearance="primary">Сохранить</DmButton>
<DmButton>Отмена</DmButton>
<DmButton appearance="subtle" density="compact">Подробнее</DmButton>
<DmButton intent="danger">Удалить</DmButton>
<DmField label="Организация" required><DmInput name="company" required /></DmField>
<DmSurface variant="filters">{/* фильтры */}</DmSurface>
```

`DmFluentDropdown` и `DmCombobox` сохраняют полный Fluent API;
`DmDropdown` — адаптер существующего value/onChange с option children.
Новые селекторы используют их. `DmSelect` остаётся совместимым нативным
контролом для существующих форм: name, required, ref, selectOption и change
events не подменяются при стилевой миграции. Его системное меню не тематизируется.
Перевод такой формы на Dropdown требует отдельной проверки валидации/отправки.

Разметка карточек может сохраняться с существующим семантическим тегом;
радиус, фон и рамка используют общие tokens. `DmSurface` подходит для новых
карточек, секций и фильтров. Не заменять form/fieldset/table на div ради стиля.
Layout, ширина, responsive композиция принадлежат feature. Не переопределять
размер/radius/focus контрола локально: применять variant или расширять адаптер.
`DmAction` сохраняет нативную семантику кнопки для строк, navigation, tabs,
choice cards и текстовых действий. Его layout может зависеть от содержания;
геометрия обычных boxed buttons остаётся в `DmButton`. `DmFileInput` сохраняет
file/ref/reset/hidden semantics. `DmDismissLayer` предназначен только для backdrop.
Обычные HTML button/input/select/textarea вне адаптера запрещены ESLint.
Для Next Link с видом кнопки: `dmLinkButtonProps` из `@marketplace/ui/link-button`.
Обычные текстовые ссылки не становятся кнопками.

Многострочный composer — `DmSurface variant="composer"` с
`DmTextarea variant="composer"`: общий focus и error border на контейнере.
Горизонтальные Fluent TabList прокручиваются внутри доступной ширины.
Popup/menu option используют общий radius8 и minimum32; dialog —16.
Pill/circle допустимы для badges/avatar, нулевой radius — для стыков поверхностей.
Ширины колонок, изображения, положение, breakpoint и декоративная геометрия
остаются локальными. Отступы, шрифт, радиусы и цвет даже в них берутся из tokens.

## Компактное редактирование на месте — решение владельца 07.10.2026

Для коротких независимых значений использовать `DmInlineEdit`: подпись и значение,
один карандаш с доступным названием; при редактировании он заменяется галочкой.
Enter сохраняет, Escape отменяет и возвращает фокус. Сохранение по blur запрещено:
переход к соседнему полю не должен отправлять случайную правку. Ошибка сохраняет
черновик, показывается у поля и не выдаётся за успех. Pending блокирует повтор.
Обязательность и допустимое значение проверяются также серверным контрактом.

Не дублировать «Изменить» отдельной большой кнопкой у каждого короткого поля.
Иконка поля видима постоянно; hover не может быть единственным способом найти
действие. `DmEditableAvatar` использует аватар48px и карандаш поверх изображения:
на hover/focus, на touch — постоянно. Отдельной кнопки рядом с аватаром нет.
Компактные элементы32px используются на desktop, на mobile область действия44px.
Размеры, цвета, типографика и focus наследуются из существующих JSON tokens.

Связанные адресные поля сохраняются одной группой: действие появляется при
изменении. Добавление контакта располагается в заголовке блока как компактное
«Добавить ещё» с плюсом; новый контакт сохраняется только после заполнения всех
обязательных полей. Личная и рабочая почта различаются: новая почта для входа
вступает в силу после подтверждения; обычный рабочий контакт не меняет логин.

Эта композиция применяется к Settings/Profile клиники и поставщика. Она не
разрешает автоматически переделывать другие страницы или отменять подтверждение
для опасных действий (например, завершения сеанса).

## Тема и проверка

Поддерживается светлая тема с Manrope из корневого layout и системным fallback.
Системная тёмная тема и прежний marketplace-theme не включают неполную dark
палитру; сохранённая настройка не удаляется. Новый dark mode требует полного
контракта и проверки всех поверхностей.

Dev-only образцы: `/dev/ui-kit`; production возвращает404.
`npm run test --workspace @marketplace/ui -- component-contract.test.ts light-theme.test.ts`
проверяет синхронизацию tokens и отсутствие неизвестных `--dm-*` ссылок.
`npm run verify:ui-contract` проверяет CSS/TSX всех приложений и packages/ui:
неизвестные tokens, raw typography/spacing/radius/colours, локальный focus,
inline control styling и CSS overrides классов shared controls. `npm run lint`
включает этот guard и ESLint границы импортов/native controls. Gates входят в CI.
Целевая browser-проверка:
`npx --no-install playwright test --config apps/e2e/playwright.ui-contract.config.ts`
при работающем canonical dev. Проверяет формы, ссылки, focus, выбор, диалог,
состояния и отсутствие горизонтального overflow при1440/390px.

При shared изменениях проверить репрезентативные реальные consumers: документы,
каталог, поставщик; light/dark OS, keyboard, disabled/error, длинные подписи.
Изменение контракта требует обновить JSON, адаптер, документацию и затронутые
проверки. Не обновлять expected лишь ради зелёного теста.

Guard обнаруживает прямые классы CSS modules и Fluent selectors; динамические
className/сложные selectors требуют review. Он не доказывает итоговый cascade,
контраст, clipping или визуальное качество. Browser-проверка изменённой поверхности
обязательна. Исходники и representative runtime покрытие описаны в
[реестре аудита](COMPONENT_CONTRACT_AUDIT.md); они не равны приёмке всех бизнес-сценариев.

и существующие `--dm-*` переменные в [styles.css](../../packages/ui/src/styles.css).

| Disabled | фон `#EEF1EF`, текст `#728078`, граница `#D7E1DC`; без opacity на всей кнопке |

Success/warning/danger/info обозначают смысл обратной связи, AI — отдельную
фиолетовую роль. Не заменять их brand-зелёным. Accent не служит фоном primary
с белой надписью. Disabled-текст не является образцом для обычного текста.

Fluent ramp направлен от тёмного к светлому. Для primary/compound actions,
ссылок, полей, focus и disabled заданы явные semantic overrides. Выбранный
checkbox использует primary и белую отметку; выбранные строки/навигация — soft
фон и тёмный content. Шапка и текущий каталог используют те же CSS-переменные.
Геометрия, навигация, логотипы, permissions и бизнес-обработчики не меняются.

Уточнение05.10 SHARED-FOCUS: общий индикатор рисуется на оболочке Fluent,
внутренний input и собственный focus-псевдоэлемент не дублируют его. У обычных
полей линия совпадает с границей; у ошибочных полей красная граница и сообщение
сохраняются, тонкий Tab-индикатор вынесен наружу. Выбранное состояние checkbox,
обычные границы, focus target и обработчики клавиатуры не изменяются. В режиме
forced colors используется системный Highlight. После Tab обычный ввод сохраняет
keyboard mode до следующего pointerdown. CSS действует также на портальные controls.

Текущий provider поддерживает только light. Сохранённая настройка marketplace-theme
не удаляется, но не включает dark. Системная тема также не переключает палитру.
Новая dark-палитра требует отдельного полного контракта и проверки.


## Выбор типографики и перенос референса

Наличие токена в шкале не означает, что он подходит любому элементу.
Основной текст использует body, подписи — caption, подзаголовки — subtitle;
крупные page/display не назначаются автоматически карточкам кабинета.
Сначала проверить принятую иерархию изменяемой страницы. Manrope подключён
в [корневом layout](../../apps/web/app/layout.tsx), с системным fallback в CSS.

Локальный принятый пример Settings/Profile: subtitle для заголовков секций,
body для текста, space-6 для padding карточки и space-4 на mobile.
Это не поручение переделать остальные страницы. Размеры shell принадлежат
общей оболочке; картинка не переопределяет их молча.

## Обязательный порядок UI-задачи и генерации референса

Решение владельца07.10.2026. Применяется к текущим и последующим задачам,
включая новый чат, восстановление контекста, генерацию изображения, редизайн
страницы и отдельного компонента. Ответственность за сверку несёт исполнитель:
пользователь не обязан замечать нарушения дизайн-системы на картинке.

### 1. До генерации или реализации: сверить основу

Прочитать этот документ, два JSON-контракта и относящийся раздел UI/UX стандарта.
Посмотреть текущую изменяемую страницу в браузере и её shared shell/компоненты
в коде. Для нового экрана взять ближайший существующий экран той же роли.
Записать в текущей карточке задачи или manifest референса краткий паспорт:

- HEAD и relevant dirty scope, роль, маршрут, viewport в CSS px и масштаб;
- ссылка на исходный screenshot и версии двух JSON;
- sidebar/header/logo, ширина контента и breakpoints;
- роли текста: font family, size, weight, line-height и соответствующий token;
- адаптеры/variants/density, высоты controls, padding/gap, радиусы и цвета;
- что именно меняется и какие общие элементы остаются фиксированными;
- обнаруженные различия runtime и контракта, выбранное основание решения.

Паспорт не копирует весь каталог токенов: содержит только параметры задачи.
В одном scope использовать существующий checkpoint/manifest, не создавать
конкурирующий backlog. Известный дефект текущего экрана не становится новым
стандартом. При недоступном runtime явно указать ограничение; не выдавать
старый screenshot за текущий и не заявлять точное совпадение без проверки.

### 2. Генерация: контракт входит в задание генератору

В prompt передать текущий screenshot как визуальную основу и параметры паспорта
явными числами, а не только словами «компактный», «как в проекте» или «Fluent».
Указать Manrope, роли/размеры текста, viewport, размеры shell, controls, карточек,
отступы и семантические цвета. Сохранить prompt и использованные источники.

Для кабинетов clinic/supplier исходная общая оболочка описана в
[UI/UX стандарте, §2.1](UI_UX_IMPLEMENTATION_STANDARD.md#21-навигация-действующего-интерфейса--30092026)
и [workspace.module.css](../../apps/web/app/workspaces/workspace.module.css).
Не брать legacy .mp-shell или публичный header вместо этой оболочки.
Сверять актуальные размеры перед задачей; не выводить их из масштаба картинки.

Генератору явно запретить изменение фиксированных shell/типографики/controls,
новые функции, блоки, действия и данные вне согласованного scope. Для редизайна
одного компонента окружающий интерфейс служит неизменяемым контекстом.

### 3. До показа как готового референса: проверить результат

Исполнитель сам сравнивает картинку с паспортом: shell, пропорции, текст,
колонки, controls, плотность, содержание. Растровая генерация не гарантирует
точные размеры, шрифт или написание; успешный вызов генератора не означает PASS.
Несоответствующую картинку исправить или пометить как концепт с конкретным
списком отклонений, не предлагать её как точный эталон реализации.

Если требование — точная геометрия/типографика, эталоном служит браузерный
макет из существующих компонентов и tokens при согласованном viewport.
Сгенерированная картинка может задавать композицию, но не заменяет измеримый
контракт. Макет создаётся в разрешённом scope; это не разрешение второго
checkout, новой дизайн-системы или изменения продукта до поручения реализации.

### 4. После одобрения: сверить перед записью кода

«Нравится», «одобряю», «сделай один в один» разрешают согласованную композицию
и реализацию, но сами по себе не отменяют действующие общие контракты.
До реализации ещё раз сопоставить выбранный референс с паспортом и правилами.

Если расхождений нет — продолжать без повторного согласования. Если есть —
назвать конкретные различия (например, заголовок32 вместо18 или другой sidebar)
и предложить реализацию композиции с действующими параметрами. Не копировать
нарушение и не исправлять утверждённый вид молча: получить только недостающее
решение по конфликтующим параметрам. Явно согласованное владельцем изменение
этих параметров имеет приоритет; повторно спрашивать его не нужно. Записать
изменение контракта/границу исключения до реализации и проверить consumers.

### 5. Приёмка: фактический интерфейс

Сравнить эталон, паспорт и screenshot результата при одинаковом viewport
и масштабе. Проверить computed styles, включая реальные input внутри адаптера
и portalled dialog/menu: наличие token в CSS не доказывает итоговый cascade.
Зафиксировать типографику, геометрию, цвета, переносы, отклонения и исправления.
Проверить относящиеся mobile/keyboard и UI состояния по риску задачи.

Сохранённый screenshot, отсутствие overflow, static guard и функциональный
PASS не равны визуальному соответствию. Финал отдельно сообщает соответствие
контракту, соответствие эталону и ограничения проверки. Нельзя утверждать
«один в один», если существенные различия остались или сравнение не выполнено.

## Обновление источника истины

1. Определить роль и consumers; не добавлять локальный дубль токена.
2. Согласованно обновить соответствующий JSON и CSS/Fluent/adapter mapping.
3. Изменения применения описать здесь; UX сценарии — в UI/UX стандарте,
   evidence — в карточке задачи. Старые страницы перехода не расширять.
4. Выбрать проверки по [Workflow](../governance/DEVELOPMENT_WORKFLOW.md):
   runtime tokens требуют синхронизации и representative consumers;
   docs-only — ссылок, согласованности и diff hygiene без app/DB/browser suites.

Общая палитра CRM/Market сохраняет согласование новой версии обоими продуктами.
Этот документ не разрешает изменять другой репозиторий или редизайн вне задачи.

## Фильтры и вкладки — решение владельца07.10.2026

Фильтр меняет набор данных: активное состояние — brand.soft фон и brand.content
текст, без нижней акцентной линии и без акцентной рамки. Hover временный,
выбранное состояние сохраняется после ухода указателя. Для DmAction используется
variant="tab" с aria-pressed; для Fluent TabList фильтра — data-dm-tab-kind="filter".
Применяется к группам заказов, актуальности товаров и фильтрам уведомлений.

Навигационные вкладки (например, Организация/Склады/Источники) сохраняют
нижнюю акцентную линию выбранной вкладки. Не добавлять боковую рамку или
внешнюю focus-тень, обрезаемую прокручиваемым TabList. Клавиатурный focus
отличается от selection внутренним hover-фоном и пунктирным подчёркиванием
текста; линия выбранной вкладки сохраняется. Pointer не включает этот focus.
При forced colors focus сохраняет системный Highlight и текстовый индикатор.
Общая внешняя рамка других controls этим исключением не изменяется.

Уточнение08.10: внутренние навигационные вкладки Settings, Import и карточки
заказа используют `DmTabList` и Fluent `Tab`: между кнопками нет внешнего gap,
внутренний горизонтальный padding12px, выбранная линия прямая, без скругления.
На узком экране одна прокручиваемая строка; навигация стрелками и видимый focus
сохраняются. Сроки акций — фильтр списка, поэтому используют фоновое выделение.

Результаты действий во всех кабинетах показываются через `useToast` или
state-driven `ActionFeedback`; `useSaveToast` сохраняется как совместимый alias.
Успех — сплошной фирменный зелёный фон, ошибка — красный; предупреждение —
янтарный, информационный результат — синий. Белый текст, семантическая иконка,
короткий заголовок и понятное пояснение обязательны. Расположение:
справа внизу viewport, отступ24px (mobile16px с safe area), пять секунд показа,
затем выезд вправо. Новое подтверждение заменяет предыдущее и начинает свой
таймер. Есть закрытие; ошибки имеют `role="alert"`, остальные — `role="status"`.
Карточка из диалога входит в его Fluent focus/announcement group и находится
выше backdrop. Закрытие возвращает фокус к исходному действию; reduced motion
отключает движение. `DmFeedback` success/danger и `ErrorState` используют карточку
по умолчанию. Постоянные состояния входа/доступа и блокирующие условия используют
`presentation="inline"`; ошибки конкретных полей, актуальность данных и бизнес-
статусы остаются рядом с содержимым. Кнопки восстановления не исчезают вместе с
карточкой, черновик сохраняется. Текст «Enter — сохранить»
не выводится; Enter/Escape продолжают работать. Важные пояснения полей размещаются
у заголовка в `DmInfoTip`, доступном по hover, keyboard focus и нажатию на мобильном.
Кнопки отмены имеют hover-фон без подчёркивания текста.
