# Локальная база и стабильный dev

Обычный `npm run dev` использует PostgreSQL `marketplace` на loopback,
единый API4012 и frontend3000. Все роли, каталог и авторизация работают
через этот API. Тестовая база по умолчанию — `dentmarket_audit_20260914`.
`DATABASE_URL` и `TEST_DATABASE_URL` могут переопределить подключения, но
локальные команды запрещают одинаковую базу, системные БД и remote/production.

## Подготовка

`npm run db:prepare:dev`

Команда требует существующую локальную базу и PostgreSQL client tools.
`POSTGRES_BIN_DIR` переопределяет каталог утилит (Windows default PostgreSQL17).
Сначала создаёт custom-format backup в ignored `.tmp/local-runtime` и проверяет
читаемость архива. Затем применяет существующие миграции. Только для пустого
каталога выполняет существующие reference/operator/import/pilot профили.
Заполненный каталог, пароли и аккаунты не сбрасываются. Незавершённый/неполный
seed требует явной диагностики; команда не пытается автоматически исправлять
существующие коммерческие данные. База не создаётся и не удаляется.

Создаёт три новых локальных аккаунта (`dev-clinic`, `dev-supplier`, `dev-operator`
на `example.invalid`) с обычным password/JWT входом, без обхода авторизации.
Случайные пароли находятся только в ignored `.tmp/local-runtime/dev-accounts.json`.
Существующий аккаунт не перезаписывается; пароль/роль при конфликте надо
разобрать вручную. Файл с паролями и backup нельзя добавлять в Git/публичные логи.

## Запуск

`npm run dev` проверяет раздельные подключения, миграции, публичную BUYER-
организацию, каталог, публикации и готовность входа. Затем собирает API и
запускает его без watcher; frontend сохраняет hot reload. После старта также
проверяет реальную публичную выдачу. При пустой выдаче сообщает проблему,
не переписывает остатки и публикации. Истечение свежести остатков остаётся
бизнес-правилом; подготовка существующей базы не продлевает её молча.

Для разработки backend: `npm run dev:watch-api` явно включает Nest watcher.
Изменения зависимостей/исходников в этом режиме могут временно прервать API.
В стабильном режиме после изменения backend нужно перезапустить dev.
Launcher не останавливает чужой процесс на занятом порту.

## Проверки

`npm run db:test -- run verify:seed-profiles` — пример отдельного запуска
проверки с тестовой БД. Не вкладывать этот wrapper в другой такой wrapper.
Обычные `verify:postgres`, `verify:pilot-backend`, `verify:core-contract` и
`verify:web` уже выбирают тестовую БД через wrapper. Прямые нестандартные
скрипты нужно запускать через `db:test` и проверять их собственный scope.
Перед E2E проверить происхождение/профиль сервера: существующий сервер dev
нельзя принимать за изолированный тестовый сервер только по номеру порта.

Публичные GET каталога, городов и проверки сессии делают не более3 попыток
при сетевой ошибке/HTTP500/502/503/504, с задержками400/1200ms и общим timeout.
Навигация отменяет запросы/таймеры. HTTP4xx и операции записи не повторяются.
После исчерпания попыток показывается честное сообщение с ручным повтором;
ошибка проверки сессии не считается успешной авторизацией или выходом.
