## Статусы и порядок работы

На входе14.10 было58 крупных пунктов, из них4 закрыты: R0.1–R0.3 и R1.1.
Добавлены48 подшагов R7.6/R7.7, все открыты. Родитель и его подшаги — один объём
работ, поэтому106 checkbox не являются знаменателем процента готовности.
Подшаг закрывается только по его собственному результату и evidence, родитель —
после всех обязательных подшагов и полного DoD, включая требуемые completion gates.

Для выбранного подшага до реализации в существующей карточке фиксируются:
текущий код и остаток, контракт/API/ошибки, backend-инварианты, UI-маршрут и состояния,
fixtures, проверки, зависимость и критерий остановки. Для UI обязательны паспорт
параметров и согласованный сценарий/макет по DESIGN_SYSTEM; конкретные endpoints,
миграции и права определяются по текущему коду. Это подготовка выбранной работы,
не требование заранее написать все детальные ТЗ проекта.

Статусные таблицы под R7.6/R7.7 — сводка того же checklist, не второй backlog:

| Поле | Как обновлять |
| --- | --- |
| Реализация | NOT_STARTED / IN_PROGRESS / PARTIAL / IMPLEMENTED; BASE означает только существующую основу, не готовность пакета |
| Проверки | NOT_RUN / PARTIAL / PASS / FAIL со ссылкой на команды, fixtures и revision; прежний PASS ограничен прежним scope |
| Публикация | NOT_PUBLISHED либо commit/ветка; BASE:SHA означает лишь опубликованную основу |
| CI | NOT_RUN / PENDING / PASS / FAIL на точном SHA; при неизвестном результате UNKNOWN, не PASS |
| Зависимость / следующий шаг | Конкретный вход или решение; владелец решения/срок уточняются при выборе пакета |

При закрытии подшага обновляются checkbox, строка родителя и evidence одной
операцией документации. Реализованный backend при отсутствующем UI даёт PARTIAL,
а опубликованный commit при failed обязательном CI не делает родителя ACCEPTED.
Исторический local PASS сохраняется даже при отдельном CI FAIL; оба факта видимы.

- `[ ]` — результат не принят; `[x]` — выполнен его конкретный критерий приёмки.
- `PLANNED` — ещё не выбран к исполнению; `IN_PROGRESS` — есть текущий исполнитель;
  `BLOCKED` — назван точный блокер; `ACCEPTED` — есть evidence нужной границы.
- `PARTIAL / NOT_ACCEPTED` — есть принятые частные результаты, но общий DoD открыт;
  эта запись не означает активную продуктовую задачу или принятую долю в процентах.
- Для результата отдельно записываются local checks, commit/push, CI и live.
  `NOT_RUN`, `PENDING` и `FAIL` не превращаются в PASS от переноса документа.
- Исполнитель указывает ID, scope, зависимости, fixtures, целевые gates и DoD
  в одной карточке текущей задачи. После проверки обновляет этот пункт и evidence.
- Текущее поручение13.10 — анализ и интеграция roadmap. Продуктовая реализация
  новых пакетов этим не запускается; выполненные прежние slices не обнуляются.

Каркас остаётся R0–R9; номера — устойчивые адреса, а не требование ждать завершения
всех внешних подключений перед независимой работой Admin или документами.
UI и целевые проверки выполняются вместе с каждым
функциональным slice: результат не ACCEPTED без необходимого пользователю
интерфейса по дизайн-системе и карты сценарий/API/маршрут/компонент/evidence.
R7 теперь содержит два крупных функциональных блока и итоговую композицию;
он не служит местом для отложенного UI всех предыдущих этапов.

а document exception — всю очередь R7.7.6. Для частичного результата указывать
точные входы/выходы и оставшийся scope, не ставить общую галочку.

До кода в существующей карточке выбранного R-ID фиксировать:

технический исполнитель может выбирать совместимые детали без новых бизнес-правил.

без второй модели состояний и без расширения разрешённого объёма задачи.

## Общая граница двух блоков и проверки

| Общая область | Владелец результата в roadmap | Приёмка пересечения |
| --- | --- | --- |
| Документ/версия/подпись/исправление/комплект | R7.6 | R7.7 читает разрешённую проекцию, не ведёт второй lifecycle |
| Операторская карточка/очередь/назначение/видимость аудита | R7.7 | Документальное исключение ведёт к исходному объекту, результат виден сторонам |
| Цена/остаток/заказ/деньги/доставка | Существующий домен, R2–R5 | Новые экраны используют его guards/events; новые интеграции учитываются один раз |
| Репутация и расчёт комиссии | R7.5 и R4 | Admin показывает проверенные факты; unknown не превращается в ноль/успех |
| Архивное восстановление и live | R8/R9 | Оригиналы/подписи/права восстановимы; реальный НУЦ и операторский доступ проверены |

Оба блока реализуются вертикальными пакетами schema/API → backend/client → UI →
целевые проверки. После каждого backend-перехода — focused tests до зависимого UI;
на завершении пакета — affected/dependent checks по Workflow. Permissions,
подписи, финансовые и конкурентные переходы требуют серверных доказательств;
UI-only screenshot недостаточен. Изменения schema требуют migration/validate/upgrade
в изоляции. Полный E2E/release — на согласованной композиционной границе R7.3/R9,
не после каждого переноса панели; лимиты попыток и прежние FAIL сохраняются.

## Обновление roadmap

После принятого slice обновите только его checkbox/статус и запись evidence:
дата, исполнитель, scope, commit плюс значимые dirty inputs, профиль/fixtures,
команды и результат, публикация/CI/live, остаток/блокер и число попыток.
Промежуточная история живёт в одной карточке, а не копируется сюда целиком.

Добавление новой идеи требует решения о составе; архивная фраза «следующий шаг»
не создаёт задачу. Если часть прежнего обязательства ещё не покрыта, сначала
сопоставьте её с ID этой таблицы, не заводите второй конкурирующий backlog.
