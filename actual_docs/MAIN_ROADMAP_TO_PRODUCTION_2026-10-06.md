## Как читать и обновлять

Утверждённое требование не равно реализованной функции. ACCEPTED относится только
к указанному объёму и evidence; LOCAL_PASS не означает push, CI или deployment.
BLOCKED/NOT_RUN остаются открытыми. Чекбоксы R перенесены без повышения статуса.
Вопрос с выбранным ответом переносится в соответствующее правило ниже; варианты
и первичная фиксация остаются в архиве. Не вести параллельные статусы в ТЗ и сводах.

Неизвестный внешний вход блокирует только зависимый результат. Для инженерной
схемы CAS, транзакций, идемпотентности, fixtures и совместимости не требуется
повторное утверждение принятого бизнес-правила. Конкретный новый выбор оформляется
в OPEN_QUESTIONS. Порядок выполнения задаёт поручение владельца, не наличие строки.

Общий DoD: сценарий → schemas/API/errors → backend/права → client → достижимый UI →
целевые проверки → evidence. Сохраняются tenant/role/version/replay/rollback,
точные деньги/stock/concurrency и recovery; UI включает состояния, RU/KK,
клавиатуру и применимую визуальную проверку. Полный E2E — только по Workflow,
не автоматически для каждой строки. Внешние receipts и production принимаются отдельно.

## Зависимости и остановка

Сначала согласованный контракт/вход выбранной ветви, затем backend и необходимый UI
одной вертикалью. П04 → П06 → П07/П08; личный checkout объединяет готовые денежные
и доставочные ветви; реальные ERP проходят по одной конфигурации. Получение/возврат
поставляют факты комиссии и агенту. Подготовка документов идёт до зависимого пути,
native следует подтверждённым API; мобильная ЭЦП имеет собственные capability/device gates.

Приёмка R7.3/R9 использует одну revision/data/provider/device матрицу. Наличие
backlog не разрешает следующий цикл, подключение сервиса, рассылку, оплату или deploy.
Проверки и переиспользование PASS — [Workflow](governance/DEVELOPMENT_WORKFLOW.md).
