## Статусы и порядок работы

На входе14.10 было58 крупных пунктов, из них4 закрыты: R0.1–R0.3 и R1.1.
Добавлены48 подшагов R7.6/R7.7, все открыты. Родитель и его подшаги — один объём
работ, поэтому106 checkbox не являются знаменателем процента готовности.
Подшаг закрывается только по его собственному результату и evidence, родитель —
после всех обязательных подшагов и полного DoD, включая требуемые completion gates.

Для выбранного подшага до реализации в существующей карточке фиксируются:
текущий код и остаток, контракт/API/ошибки, backend-инварианты, UI-маршрут и состояния,
fixtures, проверки, зависимость и критерий остановки. Для UI обязательны паспорт
параметров и согласованный сценарий/макет по DESIGN_SYSTEM; конкретные endpoints,
миграции и права определяются по текущему коду. Это подготовка выбранной работы,
не требование заранее написать все детальные ТЗ проекта.

Статусные таблицы под R7.6/R7.7 — сводка того же checklist, не второй backlog:

| Поле | Как обновлять |
| --- | --- |
| Реализация | NOT_STARTED / IN_PROGRESS / PARTIAL / IMPLEMENTED; BASE означает только существующую основу, не готовность пакета |
| Проверки | NOT_RUN / PARTIAL / PASS / FAIL со ссылкой на команды, fixtures и revision; прежний PASS ограничен прежним scope |
| Публикация | NOT_PUBLISHED либо commit/ветка; BASE:SHA означает лишь опубликованную основу |
| CI | NOT_RUN / PENDING / PASS / FAIL на точном SHA; при неизвестном результате UNKNOWN, не PASS |
| Зависимость / следующий шаг | Конкретный вход или решение; владелец решения/срок уточняются при выборе пакета |

При закрытии подшага обновляются checkbox, строка родителя и evidence одной
операцией документации. Реализованный backend при отсутствующем UI даёт PARTIAL,
а опубликованный commit при failed обязательном CI не делает родителя ACCEPTED.
Исторический local PASS сохраняется даже при отдельном CI FAIL; оба факта видимы.

- `[ ]` — результат не принят; `[x]` — выполнен его конкретный критерий приёмки.
- `PLANNED` — ещё не выбран к исполнению; `IN_PROGRESS` — есть текущий исполнитель;
  `BLOCKED` — назван точный блокер; `ACCEPTED` — есть evidence нужной границы.
- `PARTIAL / NOT_ACCEPTED` — есть принятые частные результаты, но общий DoD открыт;
  эта запись не означает активную продуктовую задачу или принятую долю в процентах.
- Для результата отдельно записываются local checks, commit/push, CI и live.
  `NOT_RUN`, `PENDING` и `FAIL` не превращаются в PASS от переноса документа.
- Исполнитель указывает ID, scope, зависимости, fixtures, целевые gates и DoD
  в одной карточке текущей задачи. После проверки обновляет этот пункт и evidence.

**Регистрация личного покупателя (решение владельца А, R7.1/R7.2/R7.3):**
короткая регистрация выбранным способом входа без обязательного полного
профиля сразу после регистрации и без привязки к клинике. Недостающие данные
покупателя, получателя и доставки запрашиваются при оформлении заказа.
Принята продуктовая основа полей: имя/фамилия и телефон покупателя; имя/телефон
получателя отдельно (по умолчанию данные покупателя); адрес при доставке либо
точка самовывоза. Email необязателен, кроме требования способа входа или
подтверждённого процесса выдачи документов; комментарий необязателен.
ИИН/дата рождения/удостоверяющие документы не обязательны без установленной
необходимости. Полная [матрица полей](UNIFIED_SPEC_MARKET_REQUIREMENTS_2026-10-29.md#personal-checkout-fields).
OPEN: внешние требования банка/перевозчика/документов, точные форматы и проверки.
Приёмка: обязательность по способу доставки, разные покупатель/получатель,
подстановка из профиля, отсутствие необоснованного требования email/ИИН; успешный личный вход
без организации/полного профиля, запрос недостающих данных в checkout, сохранение
ввода при ошибке, запрет оформления без обязательных данных/проверок.
Статус реализации NOT_ACCEPTED; существующие auth gates сохраняются.

**Личный B2C-заказ — получатель (решение владельца Б, R7.1/R7.3, R5/R7.6):**
покупатель может указать другого получателя: имя, телефон и адрес. Заказ,
документы и управление возвратом остаются у покупателя. Получатель не приобретает
права управления заказом. Применяется к P4–P7; статус реализации NOT_ACCEPTED.
Принято: код получения отправляется по SMS на телефон получателя, указанный
при оформлении личного заказа, даже если покупатель — другой человек. Получатель
сообщает код после осмотра и фактической передачи; права управления заказом
остаются у покупателя. Канал и адресат выбраны; параметры/провайдер ещё OPEN.
Принят вариант Б: после оформления изменить получателя или его телефон можно
только через обращение; самостоятельное редактирование недоступно. Обращение
само по себе не изменяет данные. OPEN: проверка заявителя, согласование и
допустимость изменения на стадии доставки, обновление данных перевозчика и
ранее выданного кода; проверка номера/получателя и обработка данных. Приёмка должна проверить
оформление на другого получателя, сохранение покупателя в документах и
запрет управления заказом только на основании данных получателя, отсутствие
самостоятельной смены получателя/телефона после оформления и путь обращения.

целевые проверки. После каждого backend-перехода — focused tests до зависимого UI;

подписи, финансовые и конкурентные переходы требуют серверных доказательств;
UI-only screenshot недостаточен. Изменения schema требуют migration/validate/upgrade
в изоляции. Полный E2E/release — на согласованной композиционной границе R7.3/R9,
не после каждого переноса панели; лимиты попыток и прежние FAIL сохраняются.

### Порядок и границы блокировок

Вход из другого R означает необходимый контракт/факт выбранного сценария, а не
обязательное закрытие всего родительского раздела. Например, R4.4.1 и R6 сначала
согласуют последствия поздней корректировки, затем проверяют совместный путь;
они не ждут полного закрытия друг друга. R7.3.1 сначала задаёт coverage, а закрывается
после сборки evidence. Контракт P1/состава не ждёт native или полного ERP live.

1. Подготовить R1-входы, R7.8.1 и R7.3.1 coverage; определить применимые provider,
   legal и data gates из существующего реестра. Неизвестный внешний вход блокирует
   зависимый результат, а не всю независимую работу.
2. Доступ/context/организации и допуск → каталог/публикация/authority. Импорт и
   подключение ERP доводятся до полезного first sync/recovery, не до одной кнопки.
3. R4.1.2 clocks → R4.1.3 composition/paid-part → P1 и provider ветви;
   B2C объединяет их с личными правами, получателем и нужным UI. Это не откладывает
   UI доменных результатов на конец R7.
4. Оплата/согласие → доставка/получение → документы/возврат → комиссия → агент и
   аналитика. Поздние корректировки учитываются в зависимых денежных результатах.
   Подготовка форм/подписей идёт до зависимой реализации; R7.6 не начинается заново.
5. Native адаптация следует подтверждённым API/coverage, mobile EDS — своей
   capability. RU/KK, доступность, безопасность и recovery проверяются внутри
   каждой вертикали. CRM-result остаётся отдельной приёмкой двух согласованных версий.
6. R8 target operations и R1.4.1 + все обязательные функциональные результаты →
   R7.3/R9 manifest/live/release → отдельно разрешённый rollout и наблюдение.

Это зависимости результатов, не поручение автоматически выполнить все пункты.
Переиспользование evidence и лимиты попыток определяет Workflow; ни один новый
checkbox не переводит прежний scoped PASS в приёмку расширенного родителя.

## Обновление roadmap

После принятого slice обновите только его checkbox/статус и запись evidence:
дата, исполнитель, scope, commit плюс значимые dirty inputs, профиль/fixtures,
команды и результат, публикация/CI/live, остаток/блокер и число попыток.
Промежуточная история живёт в одной карточке, а не копируется сюда целиком.

Добавление новой идеи требует решения о составе; архивная фраза «следующий шаг»
не создаёт задачу. Если часть прежнего обязательства ещё не покрыта, сначала
сопоставьте её с ID этой таблицы, не заводите второй конкурирующий backlog.
