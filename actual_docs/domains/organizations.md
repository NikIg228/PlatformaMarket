## Действующие требования 29.10.2026

Регистрация открыта с приватным draft; чужой БИН не выдаёт membership/доступ.
Целевой supplier путь: проверяемый источник компании/актуального директора →
автоматический compliance до первой подписи → директор собственной ЭЦП → готовый
набор offers одним подтверждением. Оператор разбирает исключения, а не повторно
проверяет каждого прошедшего supplier. Kompra/API/ИП/source freshness/legal OPEN.
Существующий ручной admission — основа, не готовый automatic KYB.
Несколько ЮЛ/филиалов/складов/точек имеют явные grants; один человек несколько org.
Личная покупка изолирована от компании; постоянная глобальная полоса buyer
context отменена 31.10. Покупатель заказа и payer сохраняются раздельно. Email/телефон/Google/Apple, безопасный link/recovery, реальные provider checks
обязательны; role/MFA/location matrix OPEN. Приглашение не выдаёт подпись.
Право сотрудников подписывать двоичное; финансовые поля — один первый руководитель
при legal DG-12. Видимость контактов и минимизация Q149 не расширяются старой
«общей публичностью» без принятой матрицы. Источник: §3–4/18/27, R1/R7.

### Уточнение по ответам Q01–Q50, перенесено 13.11.2026

По Q01/13/27/29/30 поставщик до допуска входит в кабинет, загружает прайс,
видит совпадения и готовит предложения; публикация требует реквизитов, условий
доставки, проверки компании и договора/оферты с ЭЦП. Список сотрудников не нужен
для начала регистрации. Операторский разбор исключений не разрешает bypass.
Директор назначает несколько подписантов с двоичным правом, без фиксированного
бизнес-лимита. Отзыв/истечение блокирует подпись, незавершённое действие передаётся
действующему подписанту с историей и уведомлением. Желаемое назначение без загрузки
доверенности не подтверждает юридическое основание (V26); исправления — V52.

У сетей покупателей и поставщиков юридический адрес, офис/филиал, склад и пункт
выдачи различаются; региональные цены/скидки и самовывоз из другого региона
выбираются явно, не скрытой геолокацией. Recovery через подтверждённый способ,
при утрате всех — поддержку с проверкой владельца, без передачи org/signature прав.
Усиленная проверка владельцам/администраторам/денежным ролям обязательна; полная
матрица, подписанты и ранний личный профиль — V38. Область WhatsApp/Яндекса — V44/45.

Q32/33: новые заказы ограниченного поставщика останавливаются, существующие
разбираются для исполнения/возврата с сохранением причин, истории и документов.
Замечания → исправление → повторная проверка; разблокирует уполномоченная Platforma.
Договорные основания/обжалование — V43, не произвольное удаление обязательств.

## Историческая основа и evidence до синхронизации

Ниже сохранены прежние решения и описание реализации в их датированной границе.
При расхождении целевое поведение задаёт раздел29.10 выше;
прежние решения не переопределяют новые требования.

Обновлено: 08.10.2026. Связанные этапы R1/R7/R8

### Участники и путь

Клиника закупает, поставщик продаёт, оператор допускает и разбирает исключения.
Пользователь действует от имени организации в рамках permission; принадлежность
к организации не открывает данные другой. Реферальный агент не получает доступ
к привлечённым организациям автоматически.

Путь: регистрация → подтверждение email → организация/реквизиты → условия →
необходимый допуск → рабочий кабинет. Регистрация поставщика не равна разрешению
публиковать товар. Договор и операторский допуск — разные проверки.

### Поля и интерфейс

Клинике нужны БИН, контактное лицо, телефон/email, юридический и адрес доставки.
Уточнение08.10: у клиники официальный публичный и один резервный контакт для
связи/оповещения о просрочках. По следующему ответу владельца официальные публичные
контакты клиники и поставщика доступны всем на платформе. Предусмотреть публичные
страницы обеих организаций; интерфейс и reachable переходы ещё требуют реализации
в R7. Точный состав полей берётся из официального контакта, не личного профиля.
Размещение в открытом интернете/индексация вне платформы этим решением не заданы.
Поставщику — реквизиты/склад и три обязательных контакта: официальный и два
резервных, каждый с именем, телефоном, email. Это принятое требование; полнота
текущей анкеты проверяется в R7. Официальный контакт публичен в предложениях,
резервные доступны организации, участникам заказа и уполномоченному оператору.
Личный телефон пользователя не становится публичным.

Уточнение границы второй стороны: после создания заказа поставщик видит резервный
контакт клиники, клиника — резервные контакты данного поставщика. До заказа эти
контакты второй стороне не раскрываются. В многопоставщицкой корзине связь
проверяется по соответствующему supplier order, не открывает чужих контрагентов.
Существующий доступ собственной организации и уполномоченного оператора сохраняется.
Скрытого блока UI недостаточно: границу проверять на сервере и в API response.

Существующая неполная анкета должна позволять дозаполнение без подставленных
данных. Команда/права, состояния допуска и отказ с причиной доступны соответствующей
роли. Внешняя доставка email подтверждается отдельно.
