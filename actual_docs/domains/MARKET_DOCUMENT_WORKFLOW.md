## Обязательные боевые шаблоны — решение владельца 16.10.2026

До завершения R7.6 и допуска документооборота к реальным сделкам обязательно
реализовать и принять боевые шаблоны документов согласованной цепочки: счёта,
товарной накладной, допоставки, урегулирования недостачи, исправления и возврата.
Для прочих обязательных документов определить применимость и источник:
генерация площадкой либо получение от фактического издателя. Это требование
не разрешает новые налоговые или иные внешние интеграции автоматически.

Для каждого шаблона определить назначение, форму и обязательные реквизиты,
источники данных и расчёты, нумерацию/дату/версию, подписантов и полномочия,
момент выпуска, исправления и связь с исходными документами. Содержание и
применимость согласовать с бухгалтером/юристом; реализовать печатный PDF и
необходимый UI. Приёмка включает просмотр образцов и проверки обычной/частичной
поставки, расхождений и многостраничных документов по применимости, а также
совпадение PDF с сохранёнными данными и требуемый путь подписания.

Текущий PM_INVOICE_V1 имеет механизм формирования и выставления, но окончательное
принятие формы остаётся открытым. PM_WAYBILL_PREVIEW_V1 и документы допоставки/
урегулирования — предварительные формы. PASS генерации, версий, доступа и истории
не является приёмкой боевого шаблона; подключение НУЦ само по себе её не заменяет.
Существующее evidence сохраняется только в проверенной границе.

Исполнение учитывается в существующих R7.6.1/2/4/5, сводная приёмка — R7.6.8;
новый параллельный backlog не создаётся. Первоначальный запрос только фиксировал
обязательство. Последующим поручением16.10 задача реализации передана в
«Шаблоны документов». Утверждение форм и допуск к реальным сделкам остаются открыты.

Общий контракт подготовки: отсутствующие реквизиты показываются как отсутствующие,
не заполняются именем создателя PDF или владельца аккаунта. Полномочия содержат
роль, ФИО/должность, основание, идентификатор/дату/срок документа и результат
проверки на момент подписания. Штамп «подписано» и изображение подписи не являются
заменой реального доказательства. Печатная дата операции хранится отдельно от
UTC-времени подготовки; политика локальной даты должна быть явно принята.

Новая форма получает собственную templateVersion. Старые snapshots должны
оставаться читаемыми; нельзя добавлением обязательного поля сделать недоступным
ранее сохранённый PDF. Обновление реквизитов не переписывает подписанный снимок.
Дробные количества не суммируются между разными единицами. Денежные итоги считаются
в minor units по существующей налоговой арифметике, а не по округлённому тексту PDF.

и факты. Образцы проверяются бухгалтером/юристом и владельцем до допуска к сделкам.

## 2. Граница разработки — DWF-01

В документальный scope входят генерация и загрузка документов, их связи с заказом
и фактической партией, реквизиты и нумерация, версии, проверка полномочий, план
подписей сторон, ЭЦП через НУЦ РК, фиксация действий, исправления и возвратные
документы, архив, выгрузка, необходимый UI, проверки и обусловленные моделью миграции.
Отдельная часть — SMS-подтверждение конкретного действия физлица.

Используются существующие организации, memberships, заказы, события оплаты,
партии и отправления, хранилище и адаптеры. Не включаются новые платёжные системы,
split/acquiring, движение денег, тарифы и бронирование доставки, новый checkout,
резервы, ERP-коннекторы, государственные реестры, налоговые/кассовые интеграции
или коммерческий сервис ЭДО. Недостающий вход фиксируется как зависимость;
он не даёт автоматического разрешения разработать соседнюю подсистему.

Документы частичных поставок, расхождений, исправлений и возвратов входят в целевой
процесс. Основная цепочка ниже — обязательный базовый сценарий, а не разрешение
исключить эти случаи из общей приёмки согласованного документального scope.

## 3. Принятая B2B-цепочка — DWF-02

<a id="order-pipeline"></a>

### Путь клиники от корзины — сверка реализации 15.10.2026

Каталог → корзина → «Оформить заказ» → список `/clinic/orders` → карточка
`/clinic/orders/:id` → согласование состава → счёт → оплата → отгрузки → получение.
Одна корзина с пятью товарами двух поставщиков создаёт два связанных заказа.
Карточки доступны через существующие динамические маршруты; новый файл страницы
на каждую покупку не создаётся. Поставщик работает с тем же заказом
в `/supplier/orders/:id`.

При оформлении сервер повторно проверяет условия и резервирует товар; изменение
требует принятия клиникой. Начальные статусы заказа — AWAITING_CONFIRMATION/UNPAID.
Нажатие «Оформить заказ» не списывает деньги. После частичного подтверждения
поставщиком клиника отдельно принимает состав/сумму. Поставщик формирует,
проверяет и явно выставляет счёт. В ручном пути клиника переводит деньги через
банк, сообщает о переводе с квитанцией, поставщик подтверждает поступление.
Два поставщика имеют отдельные процессы; единая банковская оплата с распределением
не заявлена готовой этим описанием.

В карточке уже есть Оплата/Отгрузки/Документы/Возвраты/История. Поставщик создаёт
отгрузку, ведёт сборку и подготовку; накладная строится по фактической партии.
R7.6.4.1 предоставляет предпросмотр DRAFT поставщику, не подписанный оригинал.
Фиксация клиникой полученного количества уже существует. Обе ЭЦП, полное
документальное закрытие и архив доказательств остаются зависимыми этапами roadmap.
Расхождения дополняют этот путь; физическое получение, подписи, комплектность
и денежный результат учитываются отдельно. Таблица ниже описывает целевую цепочку,
а не завершённость всех её шагов.

Для обычной сделки поставщик → клиника весь документальный процесс проходит
на площадке, без обязательных поездок за бумажными подписями и сбора комплекта
по переписке.

| Шаг | Действие и участник | Обязательный результат |
| --- | --- | --- |
| 1. Счёт | Площадка формирует счёт из заказа конкретного поставщика; поставщик проверяет и подтверждает выставление | Клиника видит действующий счёт, сумму, стороны и связь с актуальной версией заказа |
| 2. Товарная накладная | Формируется по фактически собранной партии; поставщик проверяет и подписывает своей ЭЦП через НУЦ | Сохранены неизменяемая версия, состав партии и проверенная подпись поставщика |
| 3. Доставка | Документы доставки прикрепляются к соответствующему отправлению через доступный канал | Их можно найти из заказа/партии; нет обещания ещё не подключённого API перевозчика |
| 4. Приёмка | Если товар совпал, уполномоченный сотрудник клиники выбирает «Принять и подписать» и подписывает своей ЭЦП тот же товарный документ | Подтверждены полномочия, нужная версия и подписи обеих сторон; расхождение запускает исправление |
| 5. Архив | Обе стороны получают свой комплект | Оригиналы, подписи, даты, история и скачивание для бухгалтерии доступны внутри площадки |

**Критерий результата:** обычная поставка без расхождений документально закрывается
внутри площадки. При расхождении не отображается ложное полное закрытие.
Если конкретной сделке необходим дополнительный налоговый документ, он входит
в комплект; отсутствие документа не маскируется успешной подписью накладной.
Документы качества/лицензии на товар и ЭСФ — разные основания и разные документы.

## 4. Участники, регистрация и полномочия — DWF-03

Регистрация: анкета и принятие условий без дополнительного обязательного SMS
или ЭЦП на этом шаге. Сохраняются текст/версия условий, организация, пользователь,
время и действие. Действующий акцепт и отдельный операторский допуск по
[ADR013](../architecture/adr/013-supplier-common-terms-and-admission.md) сохраняются.
Первая подпись накладной не является автоматическим акцептом всех условий площадки.
Обязательность договора площадка–поставщик до публикации не отменяется.

У юридического лица и ИП используются соответствующие реквизиты фактической
стороны сделки; от ИП нельзя требовать несуществующий БИН. Реквизиты сохраняются
снимком на дату документа. Изменение профиля не переписывает подписанную историю.
Новая модель реорганизации или нескольких бизнес-профилей этим не утверждается.

Сотрудник подписывает собственным ключом от имени стороны, на которую имеет
действующие полномочия. Сертификат сам по себе не заменяет проверку полномочий.
Проверка выполняется перед началом и при фиксации результата: членство, роль,
основание полномочий, срок, отзыв, сторона и допустимое действие над этой версией.
Конкурентный отзыв полномочий не должен позволять принять запрещённое действие.
Способ подтверждения основания принят в §18.1; последствия смены руководителя — открытое решение;
автоматический отзыв всех доверенностей при смене директора не утверждён.

Используются существующие роли, приглашения и ограничения. Пример «пять сотрудников»
не означает согласованный лимит «руководитель + пять». Новые накопительные денежные
лимиты подписанта, численные пороги и новая государственная интеграция не вводятся.

## 5. Матрица документов и входов — DWF-04

| Тип | Издатель / источник | Объект и событие | Подтверждение / подписи | Исправление и полнота |
| --- | --- | --- | --- | --- |
| Счёт на оплату | Поставщик; генерация площадкой из существующего заказа | Заказ поставщика, действующие условия, сумма и версия; явное подтверждение поставщиком | Подтверждение выставления отдельно от генерации; требование ЭЦП счёта не установлено | Смена существенных условий требует новой актуальной версии; старая остаётся в истории |
| Товарная накладная | Поставщик; фактически собранные позиции и количества | Партия и её связь с заказом/отправлением | ЭЦП поставщика и уполномоченного представителя клиники над одной версией | Подписанный оригинал не заменяется; исправление имеет связь с ним и собственный план подписей |
| Документ доставки | Перевозчик либо иной фактический издатель по выбранному способу доставки | Соответствующее отправление; получение через имеющийся канал | По виду и источнику документа; подписи сторон накладной не переносятся автоматически | Не подменяет товарную накладную; агрегированные чужие данные не раскрываются |
| Расхождение / исправление / возврат | По согласованной форме и событию существующего процесса | Исходный документ, партия, заявленные/подтверждённые количества и причина | Состав подписантов и момент действия требуют утверждения формы | История и оригинал сохраняются; сообщение о расхождении не равно принятому исправлению |
| ЭСФ / СНТ / фискальный документ | Фактический уполномоченный издатель, существующий источник или допустимая загрузка | Применимость к конкретной операции определяется отдельно | Проверки по виду документа; обычная ЭЦП накладной их не заменяет | Если обязателен и отсутствует, комплект неполон; новые налоговые/кассовые интеграции вне scope |
| Документ качества / лицензия | Фактический издатель и существующие сведения о товаре | Требуемые позиции/партии по действующим правилам | Проверки подлинности и применимости по принятому контракту | Не заменяет налоговый документ; точный обязательный состав уточняется |
| Документ услуг | Только при наличии соответствующей услуги и основания | Отдельная операция существующего процесса | По согласованной форме | Акт выполненных работ не добавляется к каждой продаже товара автоматически |

Нумерация использует существующие достаточные правила; маска, период, область
уникальности и допустимость номера из внешней системы уточняются с бухгалтером,
если текущего контракта недостаточно. Повтор генерации не должен выдавать второй
независимый документ для того же идемпотентного действия.

Документы связываются с конкретным поставщиком и фактической партией, а не со всей
смешанной корзиной. Не вводится произвольное правило «один заказ = одно отправление»
или консолидации: используются существующие связи. Недостающие поля/события
описываются поимённо до реализации. Изменения процесса оплаты других поставщиков
или ожидания общей оплаты корзины не следуют из этой матрицы.

## 6. Версии, переходы и комплектность — DWF-05

Названия ниже описывают смысл состояний, а не предписывают новые enum базы данных.
При реализации их нужно сопоставить с текущими контрактами.

| Переход | Кто и при каких условиях | Эффект и запрет |
| --- | --- | --- |
| Черновик → подготовлен | Генерация/загрузка после проверки входов и доступа | Фиксируется версия, источник, хеш и связи; генерация ещё не означает выставление счёта |
| Подготовлен → выставлен / ожидает подписи | Уполномоченный сотрудник стороны подтверждает документ | Проверяются актуальность и план подписей; действие привязано к версии |
| Ожидает → частично подписан | Сервер проверил подпись требуемой стороны | Фиксируется доказательство; две подписи одной стороны не заменяют другую сторону |
| Частично подписан → подписан по плану | Сервер принял все требуемые подписи нужной версии | Завершение определяется сторонами и полномочиями, а не количеством записей подписей |
| Ожидает → отклонён / требует исправления | Сторона фиксирует причину или расхождение | Нет ложного завершения; сохраняются ввод, исходный документ и история |
| Исправление → новая связанная версия/документ | По утверждённому порядку исправления | Старые подписи не переносятся; оригинал не перезаписывается |
| Завершённый документ → архивное представление | Существующий lifecycle и права | Архив сохраняет доказательства; не скрывает незавершённые обязательства комплекта |

Отдельно отображаются факт получения товара, документальное принятие,
готовность комплекта и существующие платёжные/заказные статусы.
Подписанная накладная не означает автоматически оплату, финансовое закрытие заказа
или наличие обязательного ЭСФ. Неизвестная применимость обязательного документа
требует решения и не считается доказанной полнотой.

Изменение количества, суммы или иных существенных условий делает старый документ
неактуальным для нового действия, сохраняя его доказательную историю. Запрещены
подпись устаревшей версии, незаметная замена подписанных байтов и автоматическое
подтверждение клиникой при передаче перевозчику. Передача может открыть задачу приёмки.

## 7. Подпись НУЦ и восстановление — DWF-06

Для выбранной пилотной накладной конкретная карта полей/пробелов и проект
контракта приведены в [§18](#pilot-waybill-contract). Согласованные правила
отделены от реализации и ещё не принятой окончательной формы.

**Решение владельца19.10.2026 — пилот:** единственный канал подписания —
NCALayer на компьютере: просмотр версии, выбор ключа/пароль локально, получение
CMS, серверная проверка исходных байтов/сертификата/полномочий, фиксация и архив.
Необходимые backend и UI входят в пилот; scoped prototype PASS их не заменяет.
eGov QR, eGov Mobile/eGov Business и подписание с телефона — последующие версии
в рамках R7.6.3. Нативные iOS/Android приложения также вне пилота. Мобильное
evidence остаётся NOT_RUN и не блокирует выбранный desktop-канал; это не PASS
всего будущего мобильного scope. Адаптивность ключевых страниц кабинетов сохраняется.

Выбранный путь B2B — ЭЦП через НУЦ РК. SIGEX и иной коммерческий ЭДО не являются
согласованной заменой. Наличие интерфейса адаптера в проекте не доказывает рабочее
внешнее подписание. Точный технический путь, формат контейнера и поддержка
мобильного/QR-сценария проверяются отдельным прототипом; мобильная доступность
не объявляется гарантированной до проверки.

В плане это два последовательных результата: R7.6.3.1 — доказательство технического
пути и ограничений; после фиксации контракта R7.6.1.3 — рабочий backend R7.6.3.2
и пользовательский путь/интеграционная приёмка R7.6.3.3. Закрытый прототип не
закрывает всю интеграцию. Так снимается неопределённость до массовой реализации.

Перед подписанием пользователь видит именно содержимое подписываемой версии.
Сервер проверяет связь результата с исходными байтами/хешем, версией, подписантом,
стороной и операцией, криптографическую валидность и согласованную проверку
сертификата/доверия/отзыва. Формат CMS/XML/PDF, сервисы проверки, необходимость
метки времени и долгосрочный состав доказательств выбираются техническим решением.
Это требования к продукту, а не утверждение конкретного юридического режима.

Начало, проверка, фиксация и аудит результата должны выдерживать повторы и гонки.
При неизвестном исходе внешнего действия сначала выполняется сверка состояния;
повтор не создаёт дубликат. Возврат браузера/телефона на сайт не равен успеху.
Поздно полученный результат сохраняется как доказательство даже при невозможности
принять бизнес-действие из-за отзыва полномочий или смены версии; UI различает
полученную подпись и принятое действие. Ошибка проверки не выдаётся за успешную подпись.

## 8. Частичные поставки и исключения — DWF-07

Накладная формируется на фактически собранные количества. При нескольких партиях
сохраняются их связи с позициями заказа, отправлениями и документами.
Если заказано десять, а получено восемь, пользователь фиксирует фактическое
получение, расхождение и доступные доказательства. Исходная подписанная поставщиком
накладная остаётся неизменной; создаётся задача документального исправления.

Заявление получателя о восьми единицах ещё не означает согласованное исправление
или полное документальное принятие. Формы, участники, подписи, отказ, повторная
приёмка и последствия возврата должны быть определены до запуска соответствующего
сценария. Используются события существующей товарной/денежной логики; новый
механизм возврата денег и движения остатков здесь не проектируется.

### 8.1 Проект контракта исключений — R7.6.5.1, 15.10.2026

**Статус: операционные правила согласованы владельцем 15.10.2026.** Разрешена
реализация заявления, ответа сторон и истории в интерфейсе. Формы исправления,
возврата и полномочия подписантов остаются открытыми; весь R7.6.5.1 не закрыт.
Описанная ниже модель является проектом продуктового
контракта, не утверждённая юридическая форма и не полный PASS R7.6.5.1.
Операционное заявление/ответы реализованы в выбранном пакете R7.6.5.2; см.
[границу реализации и evidence](document-workflow-implementation-log.md#discrepancy-statements). Подготовлен по поручению владельца после R7.6.4.1; НУЦ на паузе.
Существующие требования §8 сохраняются. Названия документов ниже рабочие;
официальные шаблоны, обязательные реквизиты и основания полномочий определяются
в R7.6.1.2/3 с владельцем, бухгалтером и юристом. Правовые требования здесь не устанавливаются.

#### Сценарии и результат

| Ситуация | Действие и документ | Условие завершения |
| --- | --- | --- |
| Заказано 10, в партии отправлено 8, получено 8 | Обычная накладная на 8; остаток 2 остаётся обязательством заказа | Партия может быть принята; весь заказ не закрывается из-за одной частичной партии |
| В накладной и отправлении 10, фактически получено 8 | Клиника фиксирует 8 и заявление о недостаче 2; поставщик отвечает | Согласованный способ урегулирования и отдельное документальное оформление; исходная накладная на 10 не становится принятой полностью |
| Получено 10, из них 2 повреждены | Физическое получение 10 и отдельно количество с дефектом 2, описание и доказательства | Согласованный возврат/иное урегулирование; повреждение не записывается как отсутствие товара |
| Не получено ничего | Заявление о неполучении с нулевым фактом; без искусственной единицы получения | Поставщик отвечает; документальная приёмка не возникает |
| Излишек или другой товар | Отдельное заявление с фактическим описанием | Не увеличивать согласованный заказ, сумму или полученное количество сверх партии автоматически |
| Ошибка в ранее зафиксированном количестве/реквизитах | Новое связанное исправление с причиной и ссылкой на ошибочное событие/документ | История сохраняется; прежние подписи не переносятся, существующее получение не уменьшается прямой правкой |
| Возврат уже полученного товара | Заявка на возврат, согласование, отправка обратно, получение поставщиком и отдельный возврат денег | Каждый факт подтверждён своей стороной; документальное завершение и банковский результат учитываются отдельно |

#### Предлагаемые действия и переходы

1. Клиника готовит черновик заявления по конкретному отправлению и версии
   накладной. Указывает по строкам фактическое получение, недостачу либо дефект,
   причину и доступные вложения. Наличие фото не предлагается обязательным
   условием подачи. Сохранение черновика не меняет получение, деньги и остатки.
2. «Отправить расхождение» фиксирует неизменяемую редакцию заявления, автора,
   организацию и время. Предлагаемый статус: SUBMITTED. Это операционное
   заявление, не ЭЦП и не полное принятие накладной. Если одновременно
   подтверждается допустимое получение, оно и связь с заявлением фиксируются
   одной транзакцией через существующий домен; повтор не создаёт второе событие.
3. Поставщик выбирает «Согласовать» с конкретным решением, «Отклонить» с причиной
   или «Предложить другой вариант». Встречный вариант требует явного согласия
   клиники. Согласование не меняет исходные количества и сумму само по себе.
   Предлагаемые состояния: UNDER_REVIEW, REJECTED, RESOLUTION_PROPOSED, AGREED.
4. При недостаче предлагаются два отдельных исхода: допоставка недостающего
   товара либо согласованное уменьшение обязательства с урегулированием денег.
   При допоставке сохраняются причина и связь с исходной партией; нельзя создать
   вторую оплачиваемую продажу или обойти лимит отправленного количества.
   Для уменьшения после оплаты нужен отдельный доменный переход: прежний
   pre-payment reduction и возврат физического товара его не подменяют.
5. Поставщик готовит связанный документ урегулирования/исправления. Предлагаемый
   план для двустороннего исправления и товарного возвратного документа —
   поставщик и уполномоченный представитель клиники над одной редакцией.
   Форму и момент подписания требуется согласовать. Заявление клиники сохраняет
   своего автора; ответ поставщика не переписывает заявление.
6. AGREED означает согласование решения. RESOLVED допустим лишь после исполнения
   выбранного решения и необходимого комплекта документов/подписей. Отдельно
   отображаются фактическое получение, состояние исключения, подписи, комплект
   и деньги. REJECTED не означает отсутствие расхождения или принятие товара;
   клинике доступны новая связанная редакция и обращение в поддержку.
7. Оператор рассматривает разрешённые сведения и помогает со спором. Не подписывает
   за участника, не подтверждает чужое банковское поступление, не закрывает
   расхождение за стороны. Автоматического согласия по таймеру не предлагается;
   сроки уведомлений и эскалации требуют отдельного решения.

Решение владельца17.10, R7.7.6.3: публичная рекомендация оператора с причиной
и следующим шагом завершает только обработку текущей редакции. Событие
OPERATOR_REVIEW видно клинике и поставщику в истории расхождения. Оно повышает
версию случая, но сохраняет его статус/решение и все документы, подписи,
получение, деньги и остатки. Следующий ответ стороны возвращает случай в очередь,
сохраняя назначение. Это не RESOLVED и не действие от имени участника.
GET `/operations/document-exceptions/:id` исключает черновики и приватные данные;
POST `/operations/document-exceptions/:id/recommendation` требует platform authority,
order.confirm и support.ticket.manage, версии заказа/партии/случая и idempotencyKey.
Блокировка заказа общая с командами сторон; событие, audit и outbox атомарны.
Повтор той же команды возвращает прежний результат; устаревшие версии или
изменённая команда с прежним ключом дают409. UI сохраняет ввод и требует
повторной проверки данных после конфликта. Неизвестный результат повторяется
с тем же ключом; рекомендация публикуется только после явного подтверждения.

### 8.2 Предложение по документальному закрытию довоза — 16.10.2026

**Порядок согласован владельцем 16.10.2026; юридические формы не утверждены.**
Владелец поручил реализацию и отдельно подтвердил отсутствие утверждённых форм.
Реализован только описанный ниже этап рабочих черновиков; подписанный выпуск и
RESOLVED остаются открытыми. Развивает R7.6.5.1 в узком сценарии SHORTAGE/RESUPPLY:
исходная накладная на10, получено8, согласован и получен довоз2. Возврат,
уменьшение суммы, повреждение и исправление реквизитов требуют своих правил.
НУЦ остаётся на паузе. Ниже предложен продуктовый процесс; обязательные формы,
реквизиты и юридическая достаточность остаются входом от бухгалтера/юриста.

#### Предлагаемый комплект

| Объект | Содержание и автор | Подтверждение |
| --- | --- | --- |
| Исходная накладная | Существующий оригинал на10, его версия/хеш и имеющиеся подписи | Не перезаписывается и не помечается полностью принятой задним числом |
| Заявление и решение сторон | Существующие недостача2, факт8, причина, автор, ответ и AGREED/RESUPPLY | Операционная история; согласование решения не выдаётся за ЭЦП |
| Документ связанной допоставки | Поставщик фиксирует только дополнительные2, исходную партию/заявление, отправление и фактическую приёмку | Предлагаются подписи поставщика и уполномоченного представителя клиники одной версии |
| Документ урегулирования недостачи | Поставщик составляет итог: было заявлено10, получено8, довезено и получено2, остаток обязательства по этой недостаче0 | Предлагаются подписи обеих сторон одной версии после подтверждения получения2 |

Рабочие названия двух новых документов не задают официальные формы. Предлагается
хранить их отдельными связанными объектами, чтобы различать передачу2 и итоговое
урегулирование первоначального10/8. Если утверждённая форма совмещает оба факта,
допустим один документ с обеими связями после отдельного решения по форме.
Новый счёт и новая продажа не создаются. Сумма/НДС исходной сделки не пересчитываются
операцией закрытия. При необходимости налогового исправления комплект остаётся
неполным до исполнения отдельного утверждённого требования.

#### Порядок действий и полномочия

1. После AGREED/RESUPPLY поставщик готовит черновик документа допоставки.
   Количества и ссылки берутся из согласованного заявления и связанного shipment;
   произвольное увеличение количества или создание обычной второй продажи запрещено.
2. Предлагаемый целевой порядок: поставщик подписывает документ допоставки при
   отправке; клиника после физического получения проверяет факт и подписывает ту же
   версию. При несовпадении действует отдельное расхождение, автоматической подписи нет.
   Уже исполненный операционный довоз оформляется с реальными датами событий и
   текущими датами подписей; прошлую подпись или её время система не имитирует.
3. После получения всех2 поставщик формирует итоговый документ урегулирования,
   подписывает и передаёт клинике. Клиника видит исходные10/8, дополнительную2,
   причину и ссылки, затем подписывает или возвращает на исправление с причиной.
4. Подписант каждой стороны — лицо с подтверждёнными полномочиями соответствующей
   организации. Доступ к заказу или роль сотрудника сами по себе не являются правом
   подписи. Конкретные основания и проверки полномочий ещё нужно утвердить.
   Оператор не замещает сторону; подписи двух сотрудников одной стороны недостаточно.
5. Исправление уже выпущенной версии создаёт связанную новую редакцию; прежний файл,
   подписи и отказ сохраняются. Подписи не переносятся. До новых подписей нужной
   версии исключение не закрывается; автоматического согласия по сроку нет.

#### Когда разрешён RESOLVED

Предлагается вычисляемое сервером закрытие конкретного заявления после выполнения
всех условий: решение AGREED/RESUPPLY актуально; связанная допоставка полностью
получена; нет неурегулированного расхождения по ней; обязательные документы этого
урегулирования выпущены и подписаны нужными сторонами над актуальными версиями;
проверены полномочия, целостность и результат проверки ЭЦП.

Последняя необходимая подтверждённая подпись запускает повторную проверку условий
и атомарную фиксацию RESOLVED с audit/event. Отдельной кнопки обхода условий нет.
Повтор команды не создаёт второй результат, stale version требует сверки, сбой
audit/outbox откатывает локальный переход. Получение, списание остатков, денежные
и комиссионные события при этом повторно не создаются.

RESOLVED относится к этому заявлению. Полнота комплекта заказа рассчитывается
отдельно: другие партии, исключения, обязательные налоговые/качественные документы
и подписи могут оставить заказ INCOMPLETE. В UI обеих сторон отдельно показаны
«Товар получен», «Недостача урегулирована» и «Комплект документов».

Без рабочего НУЦ доступны только явно обозначенные черновики и операционная
история. Ни кнопка согласия, ни загруженный PDF не подменяют проверенную ЭЦП;
AGREED/INCOMPLETE сохраняются. Предварительный этап без НУЦ не принимается как
реализованное документальное закрытие.

После регистрации связанного отправления поставщик с `document.issue` может
подготовить PDF-черновик допоставки. После полного получения — отдельный итоговый
черновик; поданное заявление по допоставке, включая отклонённое, блокирует его.
До регистрации отправления в текущем операционном процессе нет связанной партии:
интерфейс объясняет предусловие. Подготовка до отправки и подписанный выпуск
потребуют следующего согласованного расширения процесса.

Обе стороны с `document.view` видят версии и количества в диалоге расхождения,
скачивают сохранённый PDF. Каждый PDF явно помечен «Рабочий черновик / форма не
утверждена / не подписано». Снимок хранит исходную накладную и её версию/хеш либо
явное отсутствие, исходную и дополнительную партии, точные10/8/2, причину, автора
и время подготовки. Новая редакция сохраняет предыдущую; изменённые факты делают
старую редакцию исторической. Документы имеют kind OTHER/status DRAFT, не заменяют
накладную и не входят в комплект как подписанные оригиналы.

API: `GET /supplier-orders/:orderId/discrepancies/:discrepancyId/documents`,
`POST .../documents/prepare`, `GET .../documents/:documentId/download`.
Prepare проверяет стороны/permission, версии заказа/исходной партии/заявления/
допоставки и idempotencyKey. Транзакция под блокировкой заказа сохраняет документ,
audit/outbox; одинаковый повтор возвращает ту же редакцию, иной payload с тем же
ключом —409. Скачивание проверяет SHA256. Общие endpoints подписи и новой версии
не позволяют обойти выделенный процесс. Деньги/остатки/получение/AGREED не меняются.
Выпуск, подписи и RESOLVED не реализованы в этом этапе. Evidence и попытки —
[журнал](document-workflow-implementation-log.md#resupply-working-documents).

## 9. Подтверждение физлица — DWF-08

**Решение владельца19.10.2026:** SMS подтверждения получения и R7.6.6 отложены
за пределы пилота, требования ниже сохраняются для последующих версий. SMS входа,
проверки номера и защиты аккаунта не отменяется и не реализуется этим решением.

Пилот: уполномоченный пользователь клиники фиксирует фактическое полное/частичное
получение и расхождения по отправке/партии в кабинете; история содержит участника,
действие, объект и время. Статус доставки партнёра не заменяет подтверждение
клиники, а подтверждение получения не заменяет документальную приёмку по ЭЦП.

Последующие версии: для собственной доставки поставщика — назначенный курьер,
ограниченный мобильный веб-кабинет и одноразовый код передачи конкретной партии
на подтверждённый номер получателя. Получатель сообщает код после передачи,
курьер вводит его; сервер проверяет сессию, назначение, срок/одноразовость/лимиты.
Код фиксирует передачу, не отсутствие претензий и не приёмку всего заказа;
частичное получение/повреждения сохраняют отдельный путь. У партнёрской доставки
сначала оценивается собственное доказательство вручения, дублирование SMS не
предполагается автоматически. Самовывоз требует отдельного решения. Этот B2B
сценарий отличается от личной покупки физлица ниже; он не разрешает B2C checkout.
Нативное приложение не является обязательным условием будущего кода вручения:
первый интерфейс может быть адаптивным вебом. Исполнение ведётся в R7.6.6,
без создания отдельного конкурирующего backlog; реализация пока не начинается.

Личная покупка физлица и закупка от имени клиники различаются по стороне сделки,
а не по корпоративной/личной карте. Закупка клиники остаётся B2B с ЭЦП.
Для физлица SMS подтверждает конкретное получение/действие над заказом или партией;
код входа в аккаунт не заменяет это подтверждение и не выдаётся за ЭЦП.

Сохраняются субъект, объект, текст и версия подтверждения, время, результат и
связь с действием. Код не попадает в архив и логи. Нужны срок действия,
одноразовость, ограничение попыток и отправок; переотправка не обнуляет общий
бюджет попыток. Используются существующие утверждённые параметры; примеры
«5 минут / 5 попыток / 60 секунд» не являются выбранными значениями.

Готовность зависит от существующего личного заказа, идентификации получателя и
SMS-канала. Если их нет, зависимость фиксируется отдельно; этот документ не
разрешает новый B2C-checkout, кассу или выпуск всего B2C-продукта.

## 10. Архив и доступ — DWF-09

Архив доступен после закрытия заказа и включает оригиналы, подписи/контейнеры,
согласованные доказательства проверки, читаемые копии, даты, версии, историю,
доставку, расхождения, исправления и возвраты. Выгрузка для бухгалтерии сохраняет
связи заказ → поставщик → партия → документ → версия, подписи и контроль целостности.
Один PDF предпросмотра не заменяет оригинал с доказательствами подписи.

Каждая сторона видит только свои документы и разрешённые сведения контрагента.
Проверка tenant/role выполняется и при просмотре, и при скачивании/экспорте.
Общий документ перевозчика с данными чужих сделок остаётся в разрешённой области
площадки; контрагенту предоставляется только допустимый для него материал.

Срок хранения, legal hold, доступ после отключения организации и RPO/RTO требуют
отдельного решения. Проверяется восстановление документов, подписей и прав
существующими средствами проекта; новая инфраструктура резервирования не вводится
без доказанной необходимости и выбранного scope.

Граница доказательств: R7.6.7.3 проверяет восстановление файлов, подписей, связей
и прав на изолированных fixtures; R8.2 проверяет backup/PITR и восстановление
на целевой инфраструктуре. Функциональный документальный результат может быть
принят до полного R8; production R9 требует оба доказательства. Сроки хранения
и правила доступа остаются согласуемыми входами, а не исключаются ради приёмки.

## 11. Необходимый интерфейс — DWF-10

В существующих кабинетах клиники и поставщика документ доступен из заказа и
раздела документов. На виду: тип, стороны, заказ/партия, сумма при применимости,
действующая версия, состояние подписи и комплекта, ожидаемое действие и причина
блокировки. Действия: просмотр, подтверждение счёта, подпись, расхождение,
скачивание, история и выгрузка своих материалов по правам роли.

Нужны loading/empty/error/success, понятное восстановление после неизвестного
исхода, сохранение черновика расхождения, клавиатурный доступ и работа на
применимых мобильных размерах. После внешнего подписания показывается серверный
результат. Оператор видит разрешённые исключения и историю, но не получает
автоматического права подписывать за стороны.

Компоненты и состояния подчиняются [дизайн-системе](../ui-ux/DESIGN_SYSTEM.md).
Эта спецификация задаёт функциональный состав, не утверждает новый макет.
Массовые действия, дополнительные фильтры и отдельный редизайн не становятся
обязательными только из-за предложения команды. Нужный интерфейс входит в ту же
задачу, что серверная логика; backend без доступного пользователю действия не принят.

## 14. Приёмка и регрессия — DWF-11

Для выбранной реализации фиксируются роль, исходные данные, действие, ожидаемый
документальный результат и evidence на конкретном commit. Обязательные сценарии:

| Проверка | Ожидаемый результат |
| --- | --- |
| Два поставщика, отдельные счета и партии | Документы, суммы и права разделены; генерация → подтверждение → подпись поставщика → подпись клиники → архив проходят из кабинетов |
| Обычная поставка без расхождений | Один товарный документ подписан обеими требуемыми сторонами; комплект доступен для бухгалтерии внутри площадки |
| Обязательный дополнительный документ отсутствует | Получение/подпись показаны отдельно; комплект не объявлен полным |
| Неправильная сторона, роль, чужой tenant, истёкшие/отозванные полномочия | Запрет сервером, в том числе на скачивание и экспорт; корректный отказ без раскрытия чужих данных |
| Устаревшая версия, изменённые байты или некорректная подпись | Действие не принято; оригинал и история сохранены |
| Повтор генерации/подписи, две подписи одной стороны | Нет дублей и ложного завершения плана подписей |
| Одновременная приёмка двумя сотрудниками, отзыв прав во время подписи | Один согласованный результат; сохранены поздние доказательства и корректный бизнес-статус |
| Потерянный ответ, timeout, поздний результат | Неизвестный исход различим; сверка и повтор не создают дубликаты |
| Частичная партия, расхождение 10/8, исправление и возврат | Факты и версии сохранены, нет ложного полного принятия; применяется согласованная форма |
| SMS: неверный/просроченный/повторный код и переотправка | Привязка к действию, одноразовость и общий бюджет попыток; код отсутствует в логах/архиве |
| Выгрузка и восстановление | Оригиналы, подписи, целостность, связи и права восстановимы; чужие материалы не попадают в комплект |
| UI и recovery | Достижимые действия обеих ролей, понятные блокировки, сохранённый ввод, клавиатура и применимый мобильный сценарий |

Проверки выбираются по [Workflow](../governance/DEVELOPMENT_WORKFLOW.md):
контрактные/сервисные тесты и изолированные DB-проверки защищают инварианты;
целевой browser-сценарий подтверждает доступность пользовательского пути.
НУЦ проверяется на согласованном внешнем пути до объявления live-готовности.
События оплаты/доставки берутся из существующих контрактов или контролируемых
fixtures; тесты не разрешают новые интеграции или запись в рабочую БД.
Screenshot не заменяет доказательство криптографической проверки и полномочий.

## 15. Как использовать при разработке

1. Выбрать явно порученный scope в существующем roadmap и связанные DWF.
2. Сверить текущие код, схемы и evidence; уточнить только недостающие решения/входы.
3. Зафиксировать совместный DoD: сценарий → сущности/API → маршрут/компонент →
   состояния → проверки. Оценивать недостающую работу, не весь проект заново.
4. Реализовать контракт → backend/client → необходимый UI с целевой регрессией.
5. Записать результат и evidence в существующие roadmap/карточку/Matrix.
   Новое решение синхронизировать здесь и в затронутой сводке, сохранив историю.

Эта редакция сохраняет результат обсуждения. Сроки и трудозатраты не оценивались;
реализация, новые внешние подключения и следующая продуктовая задача не запускались.

| Документальная приёмка / исправление | Принятая версия, фактические количества, причина расхождения, ссылка на оригинал и исправление, собственный план подписей | Получение товара, заявление о расхождении и согласованное исправление |
| Комплект сделки | Применимые требования, присутствующие/отсутствующие/неактуальные документы и причина неопределённости | Статус одного документа, полнота комплекта, оплата и закрытие заказа |

Применимость комплекта должна иметь определённый источник правила и версию.
Неустановленная применимость не равна «документ не нужен». Контракт отдельно
показывает причины неполноты и неизвестности; окончательная матрица требований
поступает из решения R7.6.1.2, а не из произвольной проверки количества файлов.
Качество товара и налоговые документы проверяются как разные требования.

Документальная логика остаётся в существующем домене документов, а деньги,
остатки, отгрузка и физическое получение — в соответствующих доменах заказа.
Связь задаётся явной командой/событием и проверяемыми ссылками. Не создавать второй
заказ или вторую финансовую машину состояний ради документооборота.
Admin читает эту же модель через разрешённую проекцию по
[контракту Admin](../applications/admin-roadmap.md#implementation-contract).

### 16.2 Матрица действий и результата

| Действие | Условие и проверка при фиксации | Результат и поведение при отказе |
| --- | --- | --- |
| Сформировать счёт | Доступ к конкретному supplier order, готовые реквизиты/шаблон и текущий согласованный состав | Подготовленная неизменяемая версия для предпросмотра; счёт ещё не выставлен |
| Подтвердить выставление | Уполномоченный поставщик, ожидаемая версия заказа/документа, совпадение суммы/валюты/связей; прежние ограничения замены из order workflow | Клиника видит подтверждённый текущий счёт; конфликт требует обновить данные и вновь подтвердить, без молчаливой замены |
| Подготовить накладную | Фактически собранная партия до отправки, допустимый lifecycle отгрузки, позиции/количества и относящаяся к ним сумма | Документ конкретной партии; сумма полного заказа не подставляется автоматически для частичной отгрузки |
| Подписать поставщиком | Предпросмотр конкретных байтов, действующие полномочия своей стороны и незаменённая версия; серверная проверка подписи | Выполнена обязанность поставщика этой версии; за клинику ничего не принимается |
| Принять и подписать клиникой | Фактическое получение соответствует документу, нужная подпись поставщика и полномочия получателя подтверждены; проверяется та же версия | Документально принята партия по плану; правило изменения физического получения связывается с существующей командой без повторного движения товара |
| Заявить расхождение | Свой заказ/партия, реальные количества/причина и версия исходного документа | Зафиксировано исключение, оригинал сохранён; до согласованного исправления нет ложной полной приёмки |
| Выпустить исправление | Утверждённая форма и переход, ссылка на оригинал, актуальные данные и согласованный план сторон | Новый связанный документ/версия; подписи оригинала автоматически не переносятся |
| Открыть / скачать / выгрузить | Проверка доступа к каждому объекту и связям, включая архив и общие документы перевозчика | Только разрешённые оригиналы/доказательства; отсутствие прав не обходится ссылкой из Admin |

Принятие внешней подписи и изменение доменного состояния не должны оставлять
частично применённую операцию. До реализации определить транзакционную границу,
outbox/audit и восстановление для фактически затронутых сервисов. Позднее
доказательство сохраняется даже при отказе бизнес-действия; оно не делает старую
версию актуальной и не возвращает отозванные полномочия.

Для каждой write-команды контракт описывает входную версию, ключ и область
идемпотентности, повтор с тем же/изменённым payload, конфликт гонки, безопасную
ошибку и результат для UI. При неизвестном внешнем исходе сначала сверяется
существующая попытка, затем определяется допустимость повтора. Нельзя выдавать
универсальный «Повторить подпись», создающий новую операцию вслепую.

## 17. Счёт и общие реквизиты — решения и предложение 14.10.2026

Источник: ответы владельца на четыре вопроса о форме, нумерации, подтверждении/
замене и реквизитах. Это уточнение R7.6.1.2 и проект реализации R7.6.2,
не runtime evidence и не утверждение всех форм бухгалтером.

### 17.1 Принято владельцем

- Утверждённого образца счёта нет: площадка предлагает единый шаблон.
- Автоматическая уникальная нумерация принадлежит площадке и не зависит от
  бухгалтерской системы поставщика.
- Уполномоченный сотрудник поставщика сначала просматривает документ, затем
  явно подтверждает выставление. Оператор не подтверждает за поставщика.
- Подтверждённая версия неизменяема; исправления — новая версия и история.
  Действующие ограничения после заявления перевода сохраняются.
- Источник реквизитов — подтверждённые сведения организаций. Недостаток
  обязательных данных блокирует выставление и объясняется в интерфейсе.

### 17.2 Предлагаемая печатная форма

Один шаблон A4, преимущественно чёрный текст на белом фоне, повтор заголовка
таблицы на следующих страницах, читаемые длинные названия и отсутствие обрезки.
Platforma.Market обозначается как сервис подготовки; продавец/получатель денег —
фактический поставщик. Ниже — состав формы, а не готовый визуальный эталон:

1. «Счёт на оплату», уникальный номер, дата, версия, ссылка на заказ поставщика.
2. Поставщик: юридическое наименование/ИП, тип и значение БИН/ИИН, юридический
   адрес, контакт. Покупатель: соответствующие сведения клиники.
3. Платёжный блок: получатель, его ИИК/IBAN, банк, БИК, КБе;
   назначение платежа с номером счёта, КНП при применимости.
4. Основание: заказ; договор и срок оплаты — только если действительно заданы.
5. Таблица: №, артикул, наименование/вариант/упаковка, единица, количество,
   цена, сумма, налоговый режим/ставка и сумма НДС по строке. Явно указать,
   включает ли отображаемая цена НДС; итоговая сумма не должна его добавлять дважды.
6. Итоги: стоимость без НДС, НДС с разбивкой по ставкам/режимам, к оплате,
   валюта; для удобства сумма прописью. Скидки/доставка — отдельными строками
   только при наличии соответствующих согласованных начислений в заказе.
7. Служебный блок: кем и когда подтверждено выставление, номер версии,
   страницы. Черновик помечен явно; факт подтверждения не изображать как ЭЦП,
   не добавлять фиктивные печати/рукописные подписи.

Счёт на оплату не объявляется ЭСФ, СНТ, чеком или доказательством передачи товара.
Он не заменяет отдельные документы, применимые к конкретной сделке.

### 17.3 Предлагаемая матрица данных и блокировок

Обязательность ниже — проект продуктовой валидации, а не утверждение, что каждое
поле требуется законом для любого документа. Юридическая применимость зависит
от формы, сторон и операции; профильные подтверждения §13 сохраняются.

| Данные и источник | Счёт на оплату | Накладная/приёмка |
| --- | --- | --- |
| Подтверждённый профиль каждой стороны: юридическая форма, наименование, тип БИН/ИИН, идентификатор, юридический адрес | Обязательны для предлагаемого B2B-шаблона | Общий снимок сторон; отправитель и получатель могут отличаться от плательщика |
| Счёт поставщика: получатель, IBAN, банк/БИК, валюта, КБе | Обязательны для банковской оплаты; выбор из счетов своей организации | Не самостоятельное условие выпуска товарной накладной |
| Банковские данные клиники | Не блокируют обычный счёт поставщика | Нужны только для отдельного процесса, например возврата денег |
| Налоговый профиль с датой действия, режим каждой позиции и основание льготы при применимости | Обязательна определённость; неизвестный режим блокирует выпуск | Согласованные налоговые суммы соответствуют фактической отгрузке |
| Снимок заказа: позиции, артикул/вариант, единицы, количества, цены, скидки, валюта, точные суммы | Обязателен, только согласованная версия заказа | Дополнить фактически отпущенными/полученными количествами конкретной партии |
| Контакты, адрес доставки, склад | Контакт для связи; доставка — если согласована, не подменяет юридический адрес | Адреса/склад и ответственный из фактической отгрузки |
| Перевозчик, ТТН, доверенность, представители и основание полномочий | Не запрашивать все поля отгрузки при выставлении счёта | Заполняются по применимой форме и способу получения; не придумывать отсутствующие сведения |
| Серия/партия, срок годности, документы качества, регистрационные сведения товара | Включать, если известны и нужны для предмета заказа | Из фактически отгруженной партии; обязательность определяется видом товара и правилом комплектности |
| Номер/дата, версия шаблона, автор и подтверждение | Система + уполномоченный поставщик | Система + фактические ответственные/подписанты по утверждённому плану |

Для накладной опора — [форма З-2, приложение 26 к приказу №562](https://old.adilet.zan.kz/rus/docs/V1200008265):
она различает плановое и отпущенное количество, содержит сведения об участниках
отгрузки, транспортных документах и получении по доверенности. Поэтому перенос
реквизитов счёта экономит ввод, но не заполняет всю накладную. Применимость полей
и соответствие электронных полномочий ролям формы проверяются до её приёмки;
две подписи организаций сами по себе не доказывают заполнение всех ролей.

НДС нельзя фиксировать одной ставкой каталога. [КГД о ставках](https://astana.kgd.gov.kz/ru/news/stavki-naloga-na-dobavlennuyu-stoimost-2-163774)
указывает базовые16% и специальную ставку5% с2026 года для соответствующих
операций; [разъяснение КГД о медицинских товарах](https://almaty.kgd.gov.kz/ru/news/novye-pravila-nds-i-akcizov-chto-izmenilos-dlya-importerov-lekarstv-i-tovarov-s-2026-goda-3)
связывает применение правил с условиями и перечнями. Тип товара в маркетплейсе
сам по себе не подтверждает ставку. Хранить отдельно «без НДС», освобождение,
нулевую и положительную ставку, дату/основание правила; пересчёт прошлого
документа из сегодняшнего профиля запрещён.

### 17.4 Предлагаемая реализация

1. Расширить существующий профиль общим блоком «Реквизиты и документы»:
   юридическая форма и тип идентификатора, банковские счета, налоговый профиль
   с периодами действия. Подтверждение — авторизованным представителем с аудитом;
   форматная проверка IBAN/БИН не выдаётся за внешнюю проверку принадлежности.
   Изменение банковских реквизитов требует повторного подтверждения новой версии.
2. Общая проверка готовности возвращает конкретные отсутствующие/неверные поля
   и ссылки на исправление. Черновой просмотр допустим с явной маркировкой;
   выставление запрещено, пока обязательные данные не готовы.
3. Формат номера в реализации15.10 — `PM-INV-2026-00000001`: тип, год, последовательность
   в масштабе всей площадки. Полный номер глобально уникален; счётчик отдельный
   для типа/года, календарная зона — Asia/Qyzylorda. Маска реализует
   принятый принцип независимой уникальной нумерации. Версия `R02` дополняет
   неизменяемый базовый номер; ключ версии уникален отдельно.
4. Номер резервируется атомарно при создании полного предпросмотра до фиксации
   байтов; пропуски допустимы, повторное использование запрещено. Использовать

### 17.5 Общие данные вводятся один раз

Уточнение владельца14.10: сохранить предложенную форму счёта и общий набор
данных в документации. Состав формы — §17.2, матрица — §17.3. Организация
заполняет и подтверждает реквизиты в своём профиле; счёт, накладная и другие
применимые документы используют эти данные без повторного ручного ввода.
«Один раз» означает переиспользование с возможностью обновить профиль, а не
вечную актуальность. При изменении реквизитов подтверждается новая версия.

Общие данные: наименование/юридическая форма, БИН/ИИН, юридический адрес,
контакты, банковские счета, налоговый статус и периоды действия. Отдельно
ведутся адреса доставки/склады и представители с полномочиями. Для документа
выбираются нужные стороны, счёт и адрес; транзакционные сведения (позиции,
цены, партия, фактическое количество, дата, получатель) берутся из заказа и
исполнения. Каждый подтверждённый документ сохраняет собственный снимок.
Пользователь не правит банковские реквизиты прямо в PDF в обход профиля/аудита.

### 17.6 НДС в предложении поставщика — рекомендуемая модель

Статус: по последующему поручению владельца14.10 включено в глобальный roadmap
как [R7.6.1.4](../MAIN_ROADMAP_TO_PRODUCTION_2026-10-06.md#document-vat), PLANNED.
Это план реализации, не уже внедрённое правило и не разрешение менять
цены/налоги существующих предложений. Продуктовые проверки NOT_RUN. Общий профиль
§17.5 и эта налоговая цепочка готовят входы для счёта R7.6.2; первым независимым
шагом служат контракт и профиль реквизитов с необходимым UI. Для зависимого
расчёта остаются применимость режимов/основания, округление и переходы по датам.

**Цена для покупателя.** Поставщик вводит конечную цену за явно указанную
единицу продажи/упаковку. Для облагаемого предложения она уже включает НДС.
Каталог, сравнение, корзина и счёт используют одинаковый смысл цены; НДС
не добавляется повторно на checkout. Согласованная доставка/другие начисления
отображаются отдельно и не скрываются в налоге. У поставщика без начисления
НДС конечная цена тоже остаётся конечной, но не маркируется «включая НДС».

**Кому принадлежит режим.** Налоговый статус организации хранится в профиле,
режим продажи и ставка — в конкретном предложении поставщика, не в общей
карточке каталога. Один товар у разных поставщиков может иметь разные
обоснованные налоговые условия. Поставщик указывает применимый режим и отвечает
за достоверность своих сведений; площадка валидирует их согласованность и
сохраняет источник, автора и дату. Возможность выбора не означает произвольное
назначение любого процента.

| Выбор в предложении | Поведение |
| --- | --- |
| Облагается НДС | Допустимая ставка из версионируемого справочника с периодом действия; цена включает её |
| Поставщик не начисляет НДС согласно своему статусу | Статус подтверждён в профиле; сумма НДС не начисляется, отображается «Без НДС» |
| Освобождённая операция | Отдельный режим и основание применимости, не смешивать с отсутствием регистрации поставщика |
| Нулевая ставка | Отдельный режим и основание; не подменяет «Без НДС» |
| Не определено / противоречивые сведения | Сохранение черновика допустимо; по предлагаемому правилу публикация/покупка и выпуск счёта требуют устранения проблемы |

Список допустимых ставок и оснований зависит от даты операции, товара и условий
продажи (§17.3). Категория «стоматология» не является основанием для5%.
При неизвестной применимости не выбирать16% «на всякий случай». Налоговый статус
поставщика не даёт одну универсальную ставку всем его товарам. Массовое назначение
возможно только явно выбранным предложениям с совместимыми условиями и
предпросмотром результата. Автоматической внешней проверки КГД пока не заявляется.

**Форма предложения.** Рядом с полем «Цена для покупателя» разместить выбор
«НДС», разрешённую ставку/основание и вычисляемую подсказку «В том числе НДС…».
Для необлагаемого режима — пояснение «НДС не начисляется». При ручном вводе
предпочтительна одна конечная цена; необязательный калькулятор из цены без НДС
может вычислять её до сохранения, но не создаёт второй смысл публичной цены.
UI использует общие controls и дизайн-систему (§17.4).

**Расчёт и пример.** При конечной сумме строки G и положительной ставке r
выделение налога: НДС = G × r / (100 + r), база = G − НДС. Например,
11600 ₸ при16% содержат1600 ₸ НДС и10000 ₸ базы; итог к оплате11600 ₸.
При5% цена10500 ₸ содержит500 ₸ НДС. Это арифметические примеры, не выбор
ставки для конкретного товара. Предлагается рассчитывать после согласованных
скидок на уровне строки, округлять в minor units по единому утверждённому
правилу и суммировать строки по режимам/ставкам. Точное правило округления,
дробные количества и распределение скидок фиксируются перед реализацией;
JavaScript floating point для денежных расчётов не использовать.

**Заказ и документы.** В snapshot сохраняются конечная цена, режим/ставка,
налоговая база/НДС/итог, версия правила, основание и исходный налоговый профиль.
Перед checkout проверяется актуальность. Изменения цены/режима/ставки в активной
корзине показываются покупателю с подтверждением, даже если конечная цена
не изменилась. Для уже подтверждённого заказа, который пересекает дату изменения
налогового правила, требуется отдельный согласованный переход/исправление:
не пересчитывать историю молча и не считать фиксацию ставки в заказе заменой
правилам определения даты оборота. Счёт и накладная используют согласованные
снимки и проверяют применимость на своём этапе; корректировки сохраняют историю.

**Совместимость.** В OfferPrice, API и мастере добавления предложения уже есть
`includesVat`/`vatRate`; мастер предлагает «Включён в цену»/«Без НДС» и свободное
поле процента. Пара полей не различает все режимы выше. Расширять существующую
схему/сервис и его consumers. Старые `null` и `includesVat=false` сначала
инвентаризировать: не считать их автоматически подтверждённым освобождением
и не увеличивать цены без решения поставщика. Для ERP/импорта явно задавать,
передана gross или net цена, преобразовывать один раз до публикации, сохранять
исходный смысл и проверять совпадение; запрещён молчаливый повторный налог.

Будущие checks: один товар у двух поставщиков; разные режимы в одном заказе;
запрет противоречия профилю; неверная/неприменимая ставка; округление, скидки и
дробные количества; равенство итогов каталога/корзины/счёта без двойного НДС;
изменения статуса/ставки по дате, stale/replay, совместимость старых записей и
ERP; сохранение истории и tenant/role denial. До изменения модели проверить
сквозные consumers коммерческих условий и snapshots. Scope этой записи — docs.

#### 17.6.1 Сверка реализации и следующий контракт — 14.10.2026

Историческая подготовка; решение владельца и текущий контракт — §17.6.2 ниже.

consumers на HEAD `03828c3`; действующие цены, налоговые поля и рабочие данные

существующими контрактами, ссылки и diff hygiene; app suites для docs не нужны.

**Что расширять.** `packages/schemas/src/offer-commercial.ts` уже принимает
`includesVat` и необязательную по смыслу ставку; коммерческий редактор и мастер

а `commerce-rules.ts` сравнивает при revalidation. Значит, новые режим, основание,
версия правила и профиль должны пройти тем же путём, включая сравнение даже
при неизменной цене. Writers интеграции (`integration-execution.service.ts`) и
ручного override (`data-freshness.service.ts`) тоже записывают налоговые поля;
проверка только формы поставщика оставила бы обход общей валидации.

**Предлагаемые технические решения, ещё не runtime-контракт:**

- Режимы `TAXABLE`, `NOT_VAT_PAYER`, `EXEMPT`, `ZERO_RATED`, `UNKNOWN`.
  Для облагаемого режима — положительная ставка и версия правила; для нулевого
  и освобождённого — отдельное основание. Налоговый профиль поставщика проверять
  на применимую дату; `UNKNOWN` не превращать в нулевую ставку.
- Использовать точные decimal-строки/Decimal для ставки, количества и денег.
  Текущая `calculateLineTotal` округляет стоимость строки до minor unit через
  `ROUND_HALF_UP`. Кандидат для НДС: сначала получить согласованный конечный
  итог строки после скидки, затем округлить выделенный из него налог один раз
  тем же способом; база равна итог минус налог. Итоги документа — сумма строк,
  без повторного расчёта налога от общей суммы. Это инженерное предложение,
  а не установленное требование налогового законодательства.
- Зафиксировать в snapshot режим, ставку, основание, дату применимости,
  версии налогового правила и подтверждённых реквизитов, базу/НДС/итог строки.
  Изменение профиля/правила должно давать явный конфликт с подтверждением
  актуальных условий; ранее подтверждённый snapshot не переписывать.
- Прежние `includesVat=false`, `vatRate=null` и даже явно заданный процент
  не доказывают новый режим и его основание. До перехода нужна инвентаризация
  источников и подтверждение поставщиком; автоматический backfill ставок,
  оснований или массовая блокировка текущих предложений этим документом
  не разрешены. Для ERP отдельно определить gross/net на входе.

**Внешние основания и оставшиеся решения.** Официальное
[разъяснение ДГД от 04.03.2026](https://astana.kgd.gov.kz/ru/news/stavki-naloga-na-dobavlennuyu-stoimost-2-163774)
указывает базовые 16%, пониженные 5% с 2026 и 10% с 2027 для перечисленных операций,
с условиями, исключениями и правительственным перечнем. Оно не подтверждает
принадлежность конкретного SKU к перечню. До зависимого кода нужны:

1. Применимые основания/перечни и доказательства для ассортимента поставщиков;
   кто подтверждает их и как обновляет при изменениях.
2. Правило даты оборота и действий при смене ставки между заказом, отгрузкой

3. Подтверждение налогового округления, обработки дробных количеств,
   распределения скидок и корректировок/возвратов с примерами ожидаемых сумм.
4. План перехода прежних предложений и смысл цен в каждом ERP/импортном источнике.

#### 17.6.2 Согласованная модель и реализуемый контракт — 15.10.2026

Владелец14.10 согласовал реализацию. Состояние приёмки, Git и checks — в

описывает контракт, а не подтверждает публикацию или миграцию рабочей БД.

- Применимость режима и основания подтверждает поставщик. Площадка проверяет
  согласованность с актуальными подтверждёнными реквизитами и датой правила;
  автоматически определять принадлежность SKU перечню или проверять лицензии
  она не берётся. Режимы: TAXABLE, NOT_VAT_PAYER, EXEMPT, ZERO_RATED.
  Legacy без декларации хранится как null, а не как нулевая ставка.
- Настройка по умолчанию действует только на новые предложения. Существующие
  меняются явно: выбранные предложения → preview → подтверждение. Операция
  атомарна, сохраняет конечную цену и freshness, проверяет версии и replay key.
  Предложения ERP изменяются через настройки их источника.
- В импорте явный режим строки имеет приоритет. Для новых строк затем действуют
  default импорта и default поставщика; пустая строка обновления сохраняет
  прежнюю декларацию, включая неизвестную legacy. Неверное явное значение —
  ошибка. Server preview связывает строки, mapping, профиль и версии цен;
  устаревший preview возвращает409. Gross/net выбирается явно; net переводится
  в конечную цену один раз. Те же правила применяются к PRICE binding ERP.
- Итог строки G рассчитывается после количества и скидки. НДС = G×r/(100+r),
  один ROUND_HALF_UP до тиына, база = G−НДС. Итоги — сумма округлённых строк.
  Денежные значения показываются с двумя цифрами после запятой, включая00.
  Пример: G=100,00₸ и r=16% → НДС13,79₸, база86,21₸.
- Snapshot содержит декларацию, версии реквизитов/правила, gross/base/VAT и
  версию расчёта. Изменение налога при прежней цене требует согласования в
  корзине. Смена профиля/датированного правила требует нового подтверждения
  поставщиком; история заказа не переписывается. Существующие документы берут
  immutable order declaration для соответствующей суммы. Это не заменяет
  отдельный workflow налоговых документов и даты оборота из R7.6.2.
- UI: Настройки поставщика → НДС и PRICE-источники; создание/редактирование
  предложения; выбранные товары и массовый preview; импорт с налоговым preview;
  корзина/заказ с разбивкой. Старые данные не получают автоматический backfill.

Shared контракт: `packages/schemas/src/vat.ts`, `integration-tax.ts`, import
schemas; OpenAPI/client обновляются вместе с API. Additive migration:
`20261014020000_supplier_vat`. Применение к рабочей БД — отдельная операция.

### 17.8. Счёт заказа: контракт реализации15.10

- `GET /supplier-orders/:orderId/invoices` возвращает актуальный счёт, версии,
  readiness и причины недоступности подготовки. Поставщик видит свои черновики;
  клиника — только подтверждённые версии. Общий архив и скачивание также скрывают
  неподтверждённый счёт от второй стороны. Чтение проверяет сторону заказа и
  `order.confirm` либо `order.create`; доступ к файлу сохраняет document permission.
- `POST /supplier-orders/:orderId/invoices/prepare`: `expectedVersion`,
  `idempotencyKey`, необязательный `bankAccountId` (иначе основной счёт профиля).
  Права поставщика — `order.confirm` + `document.issue`. Сервер проверяет
  подтверждённые актуальные реквизиты, согласованный заказ, налоговые snapshots,
  суммы/валюту и ограничения оплаты/резерва. Клиент не передаёт итог или реквизиты.
- Резерв номера/версии и audit сохраняются до рендера. Ошибка рендера/хранилища
  оставляет восстанавливаемую запись; тот же ключ продолжает ту же версию.
  Предпросмотр маркирован как невыставленный и не предназначенный для оплаты.
- `ISSUE_INVOICE` в существующем order workflow принимает `documentId` и
  `previewChecksum` для GENERATED. Под блокировкой заказа повторно проверяются
  версия, реквизиты, содержимое PDF и полномочия. Подтверждение, immutable snapshot,
  ссылка текущего счёта, supersede прежней версии, workflow event/audit/outbox
  фиксируются одной транзакцией. Повтор команды возвращает прежний результат.
- Шаблон `PM_INVOICE_V1` включает платёжные реквизиты, позиции, базу/НДС/итог,
  сумму прописью, номер/версию/дату и отметку сотрудника/времени подтверждения.
  Финальный PDF имеет отдельный checksum; подтверждение в системе не является ЭЦП.
  UPLOADED/CLEAN путь сохраняется, общая генерация версий/подписей не обходит
  отдельное подтверждение GENERATED-счёта.
- UI: оплата заказа поставщика → формирование → предпросмотр → явная проверка
  реквизитов/состава/суммы → «Выставить счёт»; документы клиники → текущий PDF и
  история. Неизвестный исход записи сохраняет ключ повтора; конфликт требует нового
  предпросмотра. НУЦ, ЭСФ, накладные и рабочая миграция не входят в этот пакет.

и [checkpoint](../governance/task-state/PRIMARY-SESSION.md); этот раздел не закрывает
остальные документы и signature-часть R7.6.1/3.

### 17.9. Предпросмотр накладной партии: контракт реализации 15.10

Разрешённый объём R7.6.4.1 на время паузы SDK: подготовка и предпросмотр,
без выпуска подписанного оригинала и без документальной приёмки.

- GET /supplier-orders/:orderId/shipments/:shipmentId/waybills возвращает версии
  предпросмотра, причины недоступности и документы доставки этой партии.
  POST того же маршрута с /prepare принимает expectedOrderVersion,
  expectedShipmentVersion и idempotencyKey. Произвольные суммы, реквизиты и
  идентификаторы автора не принимаются. Обе операции проверяют принадлежность
  партии поставщику заказа и права shipment.manage + document.issue.
- Подготовка доступна в PACKING/READY оплаченного незакрытого заказа. Нужны
  актуальные подтверждённые реквизиты сторон, адрес склада/получателя, единицы
  продажи и определённые налоговые snapshots заказа. Банковский счёт не является
  самостоятельным условием накладной. При самовывозе используется адрес склада.
- Позиции берутся только из ShipmentItem выбранной партии, проверяются заказ,
  склад и предел согласованного количества. Цена и налоговый режим — из заказа;
  сумма и НДС пересчитываются по количеству партии точной денежной арифметикой.
  Сумма всего заказа не подставляется в частичную накладную.
- Под блокировкой заказа и реквизитов сохраняются Document, предыдущая версия,
  snapshot и audit. Повтор возвращает ту же запись; несовместимый повтор отклонён.
  Сбой рендера/хранилища сохраняет восстанавливаемую версию. Перед записью PDF
  входы проверяются повторно. Изменение партии/заказа/реквизитов требует новой версии.
- PM_WAYBILL_PREVIEW_V1 — предварительный PDF с номером, датой, сторонами,
  складом, получателем, перевозчиком/треком, составом, суммами/НДС и автором.
  На каждой странице есть отметка «ПРЕДПРОСМОТР — НЕ ПОДПИСАНО».
  Роли отпуска/получения и доверенность не выдумываются и не считаются заполненными
  подготовкой PDF; соответствие окончательной форме З-2 и полномочия принимаются
  вместе с рабочим подписанием. Этот предварительный шаблон не является приёмкой
  юридически завершённого оригинала.
- Файл остаётся DRAFT; signature count не означает наличия подписей. Общие
  операции подписания/перегенерации и старый document-pack не превращают такой
  предпросмотр в выпущенный документ. Черновики видны поставщику; в списки заказа
  клиники и общий комплект они не попадают. Скачивание сохраняет document.view.
- UI: заказ поставщика → отгрузки → конкретная партия → «Накладная партии» →
  подготовка → предпросмотр/PDF/история. Видны loading/error/empty, устаревание и
  причины блокировки. Неизвестный исход повторяется с тем же ключом; конфликт —
  с актуальными версиями. Мобильная таблица и управление с клавиатуры используют
  shared adapters. Создание/редактирование состава отгрузки не заменено этим шагом.

Новых миграций и рабочих изменений БД нет. Реальная подпись и полная приёмка
R7.6.4.2/3 остаются открытыми. Evidence — [журнал](document-workflow-implementation-log.md).

### 18.1 Согласованные решения и оставшиеся детали

**Последующее подтверждение владельца19.10 — актуальное решение:**

1. Руководитель назначает сотрудника с основанием, сроком и перечнем разрешённых
   документов; подтверждает назначение собственной ЭЦП. Оператор не утверждает
   каждое штатное назначение. Запись платформы не объявляется юридической
   доверенностью: необходимое основание/документ сохраняется по применимости.
2. Аккаунт связывается с ИИН отдельным действием подтверждения личности:
   подписанный через NCALayer одноразовый запрос сервера связан с пользователем
   и сессией; ИИН извлекается из проверенного сертификата. При каждой подписи
   проверяются ИИН, соответствие сертификата стороне, действующее полномочие
   и точные байты актуальной версии. Перепривязка ИИН — отдельная проверяемая
   процедура; имя/БИН из формы не дают право подписи.
3. Первичный допуск руководителя в пилоте выполняет оператор после проверки
   личности ЭЦП и основания руководства по согласованному источнику/документам.
   После допуска руководитель управляет подписантами своей организации.
   Признак руководителя в сертификате — часть проверки, не единственное основание.
4. Команда готовит форму, карту источников и примеры обычной/частичной поставки,
   НДС и многостраничного документа. Бухгалтер с опытом товарного учёта РК
   проверяет реквизиты/расчёты/применимость; юрист — полномочия, электронное
   подписание и исправления; владелец принимает процесс после устранения замечаний.

Runtime-реализация пока отсутствует; общие схемы подготовлены в §18.5.
Решения о допуске ЮЛ/ИП, поддержке, ИИН, challenge и восстановлении приняты
владельцем20.10 и уточнены в §18.6–18.8. Проверяющие формы ещё не назначены,
заключений нет. Согласование порядка не является приёмкой формы или runtime.
Перечисленные ниже первоначальные открытые варианты подтверждения полномочий
сохранены как история обсуждения и заменены этим решением.

- Пилотный канал — NCALayer desktop; QR/mobile/SMS вручения вне пилота.
- Ответ владельца19.10: подписывают **руководители и уполномоченные сотрудники
  обеих сторон**. Вариант «только первые руководители» не выбран.
- Поставщик первым подписывает накладную фактической партии; клиника при
  соответствии подписывает те же неизменяемые байты. Количество подписей одной
  стороны не заменяет другую. Физическое получение и ЭЦП — отдельные события.
- Сотрудник использует собственную ЭЦП. Роль кабинета, БИН сертификата или

- **История до согласования19.10:** кто подтверждает право сотрудника. Предложение
  для выбора: назначение руководителем с основанием, сроком и областью «накладные»;

### 18.3 Контракт версии и подписи — проект для общей схемы

Расширять существующие Document/participants/signatures и связи shipment/order;
не создавать параллельный реестр документов. До backend реализации принять
общие Zod request/response/error schemas, OpenAPI и api-client одновременно.

| Операция | Доверенные данные и вход | Результат / состояние UI |
| --- | --- | --- |
| Подготовить окончательную версию | Существующие expectedOrderVersion/expectedShipmentVersion/idempotencyKey; реквизиты/состав с сервера | PDF, checksum, версия формы, список незаполненных полей; генерация/ошибка/повтор |

| Принять CMS | Session ID и ограниченный CMS payload; browser не задаёт SIGNED, signer identity или trusted evidence | VERIFYING либо проверенный отказ; криптопроверка вне длинной DB-транзакции |

| Зафиксировать расхождение | Существующий shipment discrepancy flow, фактические количества/причина | Исходная накладная не становится полностью принятой; отдельная процедура урегулирования |

Authority reference/version в проекте — ссылка на отдельно подтверждённое основание,
не доверенная строка из запроса. Предлагаемый snapshot содержит организацию,
пользователя/проверенную идентичность, действие, основание и его файл/hash по
применимости, срок, выдавшего/подтвердившего, статус и версию отзыва. Конкретный
процесс выдачи/подтверждения принят в §18.1; детали и реализация открыты. ИП не принуждается к БИН.

План подписей задаёт требуемые стороны и порядок, привязан к версии документа.
Предлагается хранить криптографические результаты отдельно от решения о принятии
действия: поздняя валидная CMS сохраняется как evidence, но не закрывает документ
при устаревшей версии/отозванном праве. Принятые ранее подписи не удаляются при
последующем отзыве; дата проверки и snapshot полномочий остаются в истории.

Классы ошибок для будущих schema: неподходящая сторона/идентичность/полномочие,
устаревшая версия/план, несовпадение оригинала, недействительная/отозванная ЭЦП,
неполное доверие/отзыв/TSP, недоступный verifier, истёкшая/отменённая сессия.
Разделить REJECTED и INDETERMINATE; стабильные коды и HTTP mapping принять при
schema-first реализации. Сохранять стандартный envelope code/requestId/path/details.

### 18.4 Расхождения, UI и обязательное evidence

При «отправлено10, получено8» клиника фиксирует8 и расхождение2; подпись
безусловной приёмки10 блокируется. Поставщик и клиника работают по существующему
процессу урегулирования/довоза. Оригинал10 и его подписи сохраняются; согласие
с вариантом урегулирования не равно подписанному исправлению или RESOLVED.
Окончательная форма исправления/довоза принимается отдельно; текущие preview
и операционные действия не становятся подписанными от изменения контракта.

Маршрут: существующая карточка заказа → отправка → накладная. Поставщику нужны
подготовка/полнота/предпросмотр/подпись/история; клинике — просмотр поставщицкой
подписи, факт получения/расхождения и своя подпись. Оператор читает доказательства
по правам, но не подписывает за сторону. Экран показывает обе стороны, версии,
кто подписал/чего не хватает, отказ и восстановление. До UI кода нужен паспорт
по DESIGN_SYSTEM; этот документ не меняет общие компоненты/стили.

Целевые gates зависимой реализации: схема/клиент; focused сервисные проверки
после каждого перехода; изолированные DB rollback/concurrency/replay/tenant/role;
реальный NCALayer с independent verifier и сохранёнными оригиналами; актуальные
полномочия/отзыв между start и commit; несовпадение actor/сертификата/организации;
две разные стороны одной версии; 10/8 и новые версии без переноса подписей;
PDF↔snapshot, длинная многостраничная накладная и принятые налоговые случаи;
целевой UI flow обеих сторон, cancel/error/unknown/reload и доступность.
R7.6.1.2/3 не закрывать до решений и исполняемых контрактов; этот проект не PASS runtime.

### 18.5 Общие схемы пилотной подписи — 19.10.2026

В `packages/schemas/src/pilot-document-signing.ts` добавлены и экспортированы
из общего пакета request/read schemas. Это контрактный шаг R7.6.1.3, не включение
HTTP endpoints или права подписывать существующие preview-документы.

| Область | Исполняемый контракт |
| --- | --- |
| Личность | Запрос challenge без клиентского ИИН/actor/tenant/TTL; read projection с maskedIin и версией binding |
| Первичный руководитель | Заявка с версией организации, binding и документом основания; решение оператора с версией, основанием/причиной |
| Назначение сотрудника | Версии binding/membership/допуска руководителя, документ основания, конечный срок, область WAYBILL; ожидание ЭЦП не ACTIVE |
| Полномочие | ACTIVE содержит identity/basis и ссылку на операторскую проверку либо подписанное назначение; только допуск руководителя допускает неизвестный срок окончания, это не бессрочность в runtime |
| Накладная | Две разные организации SUPPLIER→BUYER; версия документа/checksum/плана и authority reference для начала подписи |
| CMS и восстановление | Session/version/CMS/idempotencyKey; AWAITING_USER/VERIFYING/UNKNOWN/COMMITTED/EVIDENCE_ONLY/REJECTED/CANCELLED/EXPIRED; позднее evidence не означает фиксацию действия |

Инженерные ограничения транспорта: base64 CMS до1MiB в декодированном виде,
challenge payload до131072 символов, replay key8–160 символов. Это локальный
контракт, не нормативные размеры; TTL10мин принят20.10 в §18.6. Перед подключением
реального endpoint лимиты сверяются с NCALayer и HTTP body limit. Парсинг CMS
только проверяет транспорт: DER, сертификат, доверие и подпись проверяет verifier.

Strict schemas отклоняют незаявленные поля; уникальность evidence и допустимый
набор подписанных сторон проверяются в read projection. Схема не доказывает
существование/доступность основания, соответствие ИИН/организации, полномочие,
порядок реальных транзакций, nonce/replay, checksum или актуальность версий.
Эти инварианты обязательны для серверных проверок start/verify/commit.

HTTP paths/status mapping и стандартный error envelope, OpenAPI и методы
api-client добавляются одновременно с соответствующим серверным маршрутом;
нынешние опубликованные операции не меняются. Для UI предусмотрены состояния
§18.3–4, но экран и backend ещё не реализованы. Приёмка формы и оставшиеся
решения §18.1 сохраняются; R7.6.1.2–3 остаются PARTIAL.

### 18.6 Решения владельца20.10: допуск, поддержка и идентичность

- **ЮЛ:** подтверждённая ЭЦП личность, документ об основании руководства,
  проверка оператором связи с организацией. Признак руководителя в сертификате
  не заменяет основание. Оператор сохраняет официальный источник/выписку,
  документ evidence, дату, автора и решение.
- **ИП лично:** личность по ИИН и регистрация предпринимателя; уведомление о
  начале деятельности с подтверждением приёма и проверка актуального статуса.
  Назначение директором не требуется. Тип основания `INDIVIDUAL_ENTREPRENEUR`
  сверяется сервером с подтверждёнными реквизитами. Нельзя требовать БИН ЮЛ.
  Уведомительный порядок — [eGov](https://egov.kz/cms/ru/articles/ip-registration).
  Точный перечень достаточных документов принимает профильный проверяющий;
  код проверки формата не объявляется юридической экспертизой.
- **Представитель ИП / сотрудник ЮЛ:** собственная проверенная личность плюс
  назначение подтверждённым предпринимателем/руководителем, основание,
  документ, срок и область WAYBILL. Представитель не становится владельцем ИП.
  Совместное предпринимательство/несовпадение представителя направляется в
  поддержку на отдельное рассмотрение, без автоматического допуска.
- **Физлицо от собственного имени без ИП** не включается в данный B2B-пилот.
  Это не ограничение пользователя-сотрудника, который представляет ЮЛ/ИП.
  Типы сертификатов физлиц/сотрудников ЮЛ различаются у
  [НУЦ](https://pki.gov.kz/ru/o-nca/); серверная политика сертификатов проверяет
  назначение операции и тип представляемой стороны, а не только наличие ИИН.
- **Смена руководителя:** только обращение в поддержку и решение оператора
  маркета; самостоятельного действия/мастера в кабинете клиента нет. Подтверждённая
  смена прекращает прежний допуск и приостанавливает выданные им полномочия до
  подтверждения новым руководителем; старые незавершённые сессии не фиксируются.
  Исполнение атомарно, с обращением, основанием и audit; ранее принятые подписи
  сохраняются. Оператор не подписывает документы вместо сторон.
- **ИИН:** первое подтверждение — одноразовый подписанный серверный challenge.
  ИИН извлекается из проверенного сертификата, не из body или реквизитов.
  Перевыпуск сертификата с тем же ИИН не меняет binding. Другой ИИН — другая
  личность; самостоятельной перепривязки нет. Ошибка исправляется через поддержку
  и отдельное решение оператора с сохранением прежней истории. Конфликт действующей
  привязки не разрешается автоматическим присвоением чужой личности.
- **Challenge/окно подписи:** ровно10мин по часам сервера; клиент не задаёт TTL.
  Для личности/назначения сервер создаёт непредсказуемый одноразовый nonce,
  включает назначение, actor/session, целевой контекст и версии в подписываемые
  байты. Для накладной подписываются именно оригинальные PDF-байты: nonce сессии
  не добавляется в PDF. Сессия хранит связь с оригиналом/версией/стороной/полномочием;
  один CMS/evidence нельзя принять за подписи разных сторон или другую операцию.
  Истёкший challenge не продлевается. Новая сессия создаётся явным действием после
  чтения результата предыдущей; сетевой таймаут сам по себе не разрешает новую.

### 18.7 HTTP и клиентский контракт R7.6.1.3

Единый исполняемый manifest — `packages/schemas/src/pilot-signing-http.ts`.
Отдельный [OpenAPI3.1](pilot-signing.openapi.json) содержит15 операций и помечен
`CONTRACT_ONLY`: эти маршруты **не зарегистрированы** в NestJS/runtime Swagger.
Клиент `@marketplace/api-client/pilot-signing` использует существующий transport
и проверяет request/response; к пользовательским экранам пока не подключён.
Старые поля `headAdmission` заменены на `principalAdmission`: первичный допуск
относится и к руководителю ЮЛ, и к ИП. Runtime consumers прежней схемы отсутствуют.

| Операции | Доступ / результат |
| --- | --- |
| GET `/identity/signing-binding`; POST `/identity/signing-binding/challenges` | Только текущий пользователь; masked binding либо session назначения BIND_IDENTITY |
| GET/POST `/organizations/{organizationId}/signing/admission` | Активный член данной организации; чтение своей заявки/допуска или первоначальная заявка с основанием ЮЛ/ИП |
| GET `/operations/signing/admissions`; GET `/{admissionId}`; POST `/{admissionId}/review` | Только оператор с capability проверки допуска; очередь, детали, проверенное решение |
| GET/POST `/organizations/{organizationId}/signing/authorities` | Чтение: рядовой член видит свои записи, допущенный руководитель/ИП — записи своей организации; создание: только руководитель/ИП |
| POST `/organizations/{organizationId}/signing/authorities/{authorityId}/revoke` | Только действующий руководитель/ИП своей организации; версия и причина обязательны |
| GET `/documents/{documentId}/signing-plan`; POST `/documents/{documentId}/signing-sessions` | Только сторона документа; план двух сторон или session назначения SIGN_WAYBILL |
| GET `/signing/sessions/{sessionId}`; POST `/signing/sessions/cms`; POST `/signing/sessions/{sessionId}/cancel` | Только владелец сессии с актуальным доступом к предмету; состояние, передача CMS или отмена |

`organizationId`/`documentId` в URL — цель проверки доступа, не источник авторизации.
Неавторизованный запрос401; отсутствие права на известный доступный контекст403;
чужой/невидимый объект404 без раскрытия его наличия. Actor/tenant только из auth.
Заявка при уже действующем другом первичном подписанте даёт `SUPPORT_REQUIRED`,
не заменяет его. Нельзя отозвать первичный допуск через endpoint отзыва сотрудника.
Операторские исполнения смены руководителя/исправления ИИН — отдельный support
workflow с audit, не скрытый параметр этих первоначальных операций.

GET списков принимает обязательные `offset`0–100000 и `limit`1–50; HTTP-адаптер
преобразует десятичные query значения в числа до проверки схемы, без permissive
`parseInt`. POST применяет строгую схему без незаявленных полей. Документы оснований
проверяются на доступ, организацию, актуальную версию и целостность. Даты источника
не должны быть в будущем. Версии binding/membership/допуска повторно сверяются
перед commit. Представитель не назначает себя сам и не расширяет scope.

Создание возвращает201; чтение/решение/отмена200; принятие CMS на проверку202.
Статус2xx не означает COMMITTED: клиент читает ресурс. Одинаковый idempotency key
в области actor+операция+предмет и тот же нормализованный payload возвращают
первоначальный результат без новых событий; другой payload —409
`IDEMPOTENCY_CONFLICT`. Проверка replay предшествует проверке устаревшей версии
после auth; ключ и digest операции сохраняются, смена TTL не разрешает повторный
commit. GET сессии возвращает текущее состояние, а не сохранённый ответ создания.

Сервер атомарно принимает CMS только при получении до `expiresAt` (равенство уже
истечение), сохраняет CMS/digest и переводит сессию в VERIFYING. Позднее окончание
проверки допустимо, но commit повторно сверяет версии/доступ/полномочия. Подлинный
поздний результат после отзыва/смены версии остаётся EVIDENCE_ONLY, не успехом.
Временный сбой verifier/неопределённое доверие — UNKNOWN и контролируемая серверная
повторная проверка сохранённой CMS; не автоматическая новая подпись на клиенте.
Отмена и commit конкурируют одной атомарной сменой состояния: commit первым →
409 `SESSION_ALREADY_COMMITTED`; отмена первой → никаких последующих бизнес-эффектов.

Ошибки используют совместимый core envelope `statusCode/code/message/path/
requestId/timestamp/details`. Mapping зафиксирован в `pilotSigningHttpStatus`:
409 для версий/полномочий/состояния/replay,422 для некорректной подписи/сертификата
и несоответствия личности/стороны,503 для unavailable/indeterminate,413 для лимита,
429 для ограничения запросов. В details допустимы только доступные sessionId и
currentVersion; ИИН, CMS, сертификаты, токены и внутренние исключения не выдаются.
Завершённый REJECTED читается как ресурс200 с reasonCode;503 при отправке не
доказывает, что запрос не принят — сначала GET состояния той же сессии.

### 18.8 UI-state map и граница проверки контракта

| Поверхность | Состояние → действие |
| --- | --- |
| Личность | UNVERIFIED → подтвердить через NCALayer; VERIFIED → masked ИИН; исправление только через поддержку |
| Первичный допуск | Нет заявки → основание ЮЛ/ИП; PENDING_REVIEW → ожидание; REJECTED → причина/новая исправленная заявка; APPROVED → управление подписантами |
| Назначение | Черновик → подготовить; AWAITING_PRINCIPAL_SIGNATURE → ЭЦП руководителя/ИП; ACTIVE → срок/область/отзыв; SUSPENDED → обращение/подтверждение через предусмотренный процесс |
| Оператор | Очередь → личность/основание/источник → approve/reject с причиной; смена руководителя приходит из поддержки |
| Подпись | AWAITING_USER → NCALayer/отмена; VERIFYING → ожидание; UNKNOWN → проверить состояние без повторной подписи; COMMITTED → обновить binding/authority/план |
| Ошибка/поздний результат | REJECTED → причина; EVIDENCE_ONLY → действие не принято; CANCELLED/EXPIRED → прочитать актуальный предмет и явно начать новую сессию |

Каждая поверхность также имеет loading/empty/error с сохранением ввода и
возможностью повторного чтения. Накладная скачивается существующим авторизованным
`GET /documents/{documentId}/download`; клиент проверяет hash полученных байтов
перед NCALayer, сервер независимо проверяет оригинал. Preview guards сохраняются.
Маршруты UI: существующие личный профиль, команда организации, операторская
проверка и карточка заказа; визуальный паспорт нужен перед UI-кодом.

Генерация: `npm run build --workspace=@marketplace/schemas`, затем
`node scripts/generate-pilot-signing-contract.mjs`; проверка сохранённого artifact —
та же команда с `--check`. Cross-field refinements и авторизация не выражаются
полностью JSON Schema: сервер обязан применять Zod и доменные проверки.
Schema/client tests не доказывают реальную криптографию, tenant isolation,
транзакции, scheduler/recovery или доступность UI. Для них сохраняются gates§18.4.
Контракт начального пилотного потока подготовлен; полные R7.6.1.2–3 остаются
PARTIAL из-за формы и отдельных операторских процедур исправления/смены.
