# Рейтинги поставщиков и отзывы клиник

Обновлено: 08.10.2026. Обязательны уже в пилоте; исполнение R7.5
[roadmap](../MAIN_ROADMAP_TO_PRODUCTION_2026-10-06.md).

## Два отдельных результата

Автоматический trust score0–100 строится по событиям: наличие20%, цена15%,
исполнение20%, подтверждение10%, доставка10%, документы10%, коммуникация5%,
свежесть5%, споры5%. Окно180 дней, полураспад90; до5 metric events числовой
результат отсутствует. Текущий prior0.78 с весом3 — техническая методика,
не новая утверждённая владельцем бизнес-политика.

Отзывы — отдельная общая оценка1–5 и семь критериев. Среднее звёзд автоматически
не является trust score. Точные формулы/параметры и evidence сохранены в
[сверке R1](../governance/task-state/R1-LAUNCH-SCOPE-2026-10-08.md).

## Форма клиники

Решение владельца08.10: отзыв полностью доброволен. Клиника может не оставлять
его; отсутствие отзыва не блокирует заказ и дальнейшую работу. Обязательного
ответа «Не могу оценить» нет. Обязательность самой функции в пилоте не делает
её использование обязательным для клиники.

Вход из своего заказа; поставщик/заказ определяются сервером.
Общая оценка1–5 без значения по умолчанию. По решению владельца отдельные
критерии можно оставить пустыми: одной общей оценки достаточно для отправки.
Комментарий необязателен, максимум4000 символов; связь с вариантом товара —
только из этого заказа. Уже созданный отзыв показывается вместо второй формы.

Применяются общие field/textarea/button adapters, доступная шкала с label,
клавиатурой и focus. Если варианта нет, расширяется shared adapter.
Нужны validation/loading/submitting/error/retry, сохранение ввода,
различимые публикация/модерация, редактирование14 дней и version conflict.

API сейчас требует все7 числовых оценок даже при CANCELLED/REJECTED; это разрыв
с принятым необязательным заполнением. В R7.5 изменить schema/API/client/UI
согласованно. Пропуск не становится нулём, пятёркой или общей оценкой.

## Отзыв после получения — решение и проект сценария08.10

Владелец предложил последовательность по описанному им принципу Яндекс.Go:
звёзды → интерактивные иллюстрированные причины → необязательный текст.
Внешний интерфейс не копируется; тематика, компоненты и визуальные параметры
соответствуют дизайн-системе маркета. Это требования к R7.5, не реализованный UI.

После подтверждённого сервером получения заказа предложить клинике оценить
поставщика: контекст заказа, его имя, вопрос «Как прошёл заказ?» и шкала1–5.
Ничего не выбрано заранее. Доступны закрытие/«Не сейчас» и возврат к отзыву
из заказа. Закрытие не отправляет отзыв, не меняет статус заказа и не штрафует
клинику. Отправка только отдельным явным действием.

После выбора5 звёзд показать положительные карточки с тематическими иллюстрациями;
для1–3 — причины недовольства. Для4 звёзд **принят владельцем** тот же положительный
набор и необязательный комментарий «Что можно улучшить?».

| Тематика/образ | Положительная карточка | Причина недовольства |
| --- | --- | --- |
| Коробка и часы | Быстро отгрузили | Долго не отгружали |
| Диалог | Быстро отвечали | Долго ждал ответа |
| Заказ и отметка | Всё по заказу | Не тот товар или фасовка |
| Набор коробок | Всё в комплекте | Не хватило товаров |
| Защищённая упаковка | Надёжно упаковано | Повреждённая упаковка |
| Маршрут и часы | Доставили вовремя | Доставка задержалась |
| Документ и отметка | Документы в порядке | Проблемы с документами |

Семь пар — предложение текстов и иллюстративных тем для реализации. Карточки
выбираются независимо, несколько или ни одной; повторное нажатие снимает выбор.
Низкая оценка также отправляется без причин и текста. Не приписывать задержку
перевозчика поставщику автоматически: это мнение клиники, не доказанный metric event.

При смене группы оценки несовместимые выбранные причины перестают отправляться;
смена набора понятна пользователю, общий комментарий сохраняется. Положительный
отзыв не получает более простой путь публикации, чем отрицательный. Не вводить
поощрение только за высокую оценку или обязательное объяснение низкой.

Принято владельцем08.10: одно автоматическое приглашение после полного получения
заказа; после закрытия не показывать автоматически снова, оставить действие
в заказе. При частичном получении дождаться завершения. Отображать сотруднику,
подтвердившему получение; область дедупликации между сотрудниками уточнить при
контракте. Дополнительные автоматические напоминания не вводятся. Не менять
существующие права на отзыв по другим статусам молча ради этого триггера.

## Контракт карточек и приёмка

Карточки причин — отдельные стабильные коды с версией набора, не семь обязательных
числовых оценок и не преобразование выбранной причины в скрытые5/1 баллы.
До реализации определить Zod/request/response, хранение и совместимость старых
отзывов, допускаемые коды/группы, правила редактирования и публичное отображение.
Пересчёт агрегатов учитывает только реально поставленные оценки; пропуски
не занижают результат. Коды причин сами не переписывают автоматический trust score.

Использовать shared control для шкалы и выбора карточек. Иллюстрация не заменяет
текст; label/selected state, клавиатура/focus и доступность обязательны.
До рисунков/референса/реализации — паспорт параметров и два JSON-контракта
дизайн-системы. Здесь визуальные assets и новые стили не создаются.

Целевая проверка R7.5: отзыв только со звёздами; добровольный пропуск; несколько
причин;1–3 и5 звёзд; согласованный путь4 звезды; смена группы; сохранение ввода
при retry; отсутствие дубля/повторного приглашения; своё/чужое получение;
legacy reviews, version/idempotency, модерация и keyboard/mobile visual acceptance.

## Текущая основа и недостающие связи

Есть score engine, review/response/moderation/appeal с историей.
Автоматический поток реальных order/payment/delivery/import фактов в метрики
не принят; synthetic seed и ручная запись этого не доказывают.
Полный clinic/supplier/operator путь apps/web и включение trust в pilot
требуют работы; legacy UI не означает доступность в каноническом кабинете.
Ответ поставщика, жалоба, модерация/апелляция входят в тот же результат.
