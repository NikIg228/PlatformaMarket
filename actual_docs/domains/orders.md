## Согласование заказа: 25 решений владельца от 31.10.2026

Статус: **бизнес-решения приняты; таблица переходов подготовлена для реализации**.
Это не утверждение о текущих API/enum, работающем UI или PASS R4.1.2–3.
Единственный реестр исполнения — [roadmap](../MAIN_ROADMAP_TO_PRODUCTION_2026-10-06.md#order-agreement-execution).
Этот раздел — каноническая запись ответов викторины 1–25, включая последующие
уточнения владельца. Номера относятся к этой викторине, не к исходным Q объединённого ТЗ.
Область: клиника и разрешённый B2C, отдельный заказ каждого продавца.
Последние решения ниже заменяют прежнее OPEN по тем же вопросам DG-03/06,
но не закрывают банковские, правовые и технические зависимости целиком.

### Принятые бизнес-правила

| № / ответ | Правило для реализации |
| --- | --- |
| 1А, уточнён 16 | Рабочий час ответа считается по обязательному графику поставщика: дни, часы, перерывы, исключения. Остаток часа переносится на следующий рабочий интервал. Последующее изменение графика не переносит срок уже поступившего заказа. |
| 2А | От поступления доступного заказа: одно напоминание после 45 рабочих минут; после 60 — просрочка и уведомление; после 120 — одна задача оператору при отсутствии содержательного ответа. Это не обязательный звонок на 61-й минуте. |
| 3А | Повторное согласие покупателя нужно только при изменённых условиях. Подтверждение поставщиком неизменного заказа ведёт к предусмотренной оплате/исполнению без второго согласия покупателя. Предложение изменений актуально 24 непрерывных часа; после истечения поставщик повторно проверяет условия и публикует актуальную версию с новым сроком. Нет отдельного молчаливого продления, автоматического согласия/отмены/refund/резерва. |
| 4А | Покупатель принимает предложение целиком, включая состав, количество, цену, доставку и связанные скидки/подарки. Выборочное принятие отдельных изменений не формирует действующий состав. Для иного варианта нужны замечания и новое предложение. |
| 5А | Новая опубликованная версия заменяет предыдущую, покупатель уведомляется, прежняя версия недоступна к принятию. Новая версия имеет свои 24 ч, история и общее ожидание сохраняются. Если прежняя уже принята, следующая правка — новое предложение; прошлое согласие не переписывается. |
| 6Б | При несогласии покупатель выбирает «Обсудить другой вариант» либо «Отменить заказ у этого поставщика». Обсуждение сохраняет согласование; отмена проходит допустимый для стадии маршрут, не обходит pending/unknown/оплату/отгрузку. Другие продавцы не затрагиваются. |
| 7А | «Предложить изменения» от покупателя содержит пожелания и комментарий. Поставщик проверяет исполнение и формирует итоговое предложение, покупатель явно принимает его. Пожелание само не меняет обязательство. |
| 8А | Если поставщик предлагает изменить согласованный неоплаченный заказ, новая оплата затронутого заказа приостанавливается до решения. Иные продавцы не блокируются. Начатый платёж не считается отменённым — сначала выясняется его результат. |
| 9А | Одно напоминание покупателю через 12 непрерывных часов после публикации ещё актуального предложения. Отправка переносится в разрешённое время; если к этому моменту предложение принято, отклонено, заменено или истекло — напоминание не отправляется. Deadline не сдвигается. |
| 10А | Специальный запрос покупателя на изменение оплаченного заказа блокирует передачу затронутой неотгруженной части в доставку до решения. Обычное сообщение в чате не блокирует. Если передача уже зафиксирована — маршрут расхождения/возврата, без обещания остановить её. |
| 11А | Независимая согласованная и полностью оплаченная часть может исполняться, если отделение не меняет общую скидку, подарок, стоимость или условия доставки. Иначе связанные изменения согласовываются вместе. Нельзя молча увеличить плату за доставку. |
| 12А, уточнение | Изменение после оплаты — исключение: согласованная просьба покупателя либо невозможность полного исполнения, например брак/недостача. При явно согласованном уменьшении неотгруженной части продавец обязан вернуть разницу покупателю. Автоматического внутреннего баланса нет; до подтверждённого возврата остаётся обязательство продавца. |
| 13А | При проблеме с оплаченным товаром покупатель выбирает из доступных вариантов поставщика: ожидание, конкретная замена, отмена проблемной части с возвратом. Для каждого варианта явны товар/количество, цена и срок. Молчание не разрешает замену или перенос срока. |
| 14А | Если предложение по проблемной оплаченной части истекло без ответа, создаётся одна задача оператору Market. Проблемная часть не отгружается; деньги и обязательства сохраняются. Оператор не принимает условия за покупателя; автоматической отмены/замены нет. |
| 15А | В заказе видны причина, сумма и состояния «Ожидается возврат», «Возврат отправлен», «Возврат подтверждён». Заявление продавца об отправке не закрывает обязательство. Источник подтверждения зависит от платёжного пути. |
| 16, свой вариант | Поставщик сам заполняет календарь. Компонент лишь помечает даты праздников Казахстана; работать в праздник или нет решает поставщик. Праздники не становятся нерабочими автоматически. Это уточняет 1А и заменяет предложенную автоматическую праздничную основу. |
| 17А | Напоминания покупателю отправляются 09:00–20:00 по выбранному часовому поясу; при отсутствии выбора — время Казахстана. События в кабинете видны сразу,24 ч идут и ночью. Ограничение не относится к SMS-кодам входа/получения. |
| 18А | Исходный час ответа поставщика не продлевается. «Нужно больше времени» может информировать покупателя, но не считается подтверждением, конкретным предложением изменения или отказом с причиной. |
| 19А | После отклонения изменений с выбором обсуждения прежняя версия доступна к оплате только после явного подтверждения поставщиком её исполнимости. Автоматического возврата к оплате старых условий нет. |
| 20А | Покупатель может отозвать собственный незавершённый запрос. Если он остановил исполнение, поставщик подтверждает продолжение по прежним условиям. Уже принятое изменение отзывом не отменяется. |
| 21А | От клиники согласует любой сотрудник с действующим правом оформления/согласования и доступом к нужному филиалу. Записывается конкретный actor. Личную покупку согласует сам покупатель; получатель не приобретает это право. |
| 22А | Оператор связывается, объясняет и ведёт спор, но не принимает изменения за стороны. Обычный звонок не создаёт согласие в системе. |
| 23А | Продавец обязан инициировать согласованный возврат не позднее следующего рабочего дня после фиксации суммы и основания. Срок зачисления банком отдельно. Договорная применимость и платёжная выполнимость требуют внешнего подтверждения; это не утверждение о законе или банковском SLA. |
| 24А | При пропуске срока инициирования возврата — видимая просрочка, уведомления продавцу/покупателю и одна задача оператору. Автоматические штрафы и запрет новых заказов этим решением не вводятся. |
| 25А | Для ручного перевода сведения/доказательства продавца дают «Возврат отправлен». Получение подтверждает покупатель; при отсутствии подтверждения или споре оператор сверяет доказательства. Молчание не получение. Для автоматизированного возврата нужен проверенный платёжный источник. |

### Контракт реализации и критерии проверки

- Связь: сценарий → supplier order/часть → composition/proposal version → конкретный
  actor/право → согласие → payment allocations → shipment/refund → UI/evidence.
- До реализации схем определить поля snapshot графика/timezone, entered/issued/expiresAt,
  base/target version, reason, idempotency key, authority и audit/outbox effect.
  Это проект технического контракта, не объявление полей существующими.
- Рабочий час начинается, когда заказ зафиксирован и доступен в кабинете; задержка
  доставки уведомления/непрочтение не сдвигают его. 24 ч отсчитываются от публикации
  доступной версии и постановки уведомления в отправку. Эти факты фиксируются
  транзакционно с outbox; повтор delivery не начинает новый срок.
- Техническая граница для проекта тестов: принятие требует serverNow < expiresAt;
  на границе и позже — expired/conflict. Использовать серверные часы, календарные
  snapshots и явный timezone, не часы браузера. Это деталь проектирования, не новый
  бизнес-срок. После реального изменения публикация новой версии получает новый 24 ч срок;
  retry/no-op не обновляет deadline. Час первого ответа и общая история не обнуляются.
- Согласия и holds проверяются вместе с текущей версией перед оплатой/отгрузкой.
  Входящий подтверждённый денежный факт не отбрасывается из-за смены версии;
  размещение средств и право отгрузки требуют отдельной сверки.
- Для UI обязательны полный diff и итог до принятия, причины блокировки оплаты/передачи,
  countdown с понятной датой, история версий/участников, два действия несогласия,
  статус запроса, восстановление после conflict и отдельная панель возврата.
  Ошибка/повтор сохраняют ввод; keyboard/mobile/RU/KK входят в приёмку выбранной вертикали.
- Перед зависимым UI: schema/request/response/error, OpenAPI/client и focused API/DB
  tests. В T01–T17 доказать happy/invalid path, tenant/owner/branch denial,
  idempotency/concurrency/rollback, stock и деньги в minor units; не доказывать их screenshot.
  Доменный результат принимается вместе с нужным UI. Точные команды/fixtures выбираются
  по Workflow на фактическом diff, миграции только на disposable DB.
- Покрытие ответов: 1/2/16/18 → T02; 3/4/5 → T01/T03–05/T07; 6/7/8/19 →
  T03/T06/T08/T13; 9/17 → T07; 10/11/20 → T09/T10/T12/T17; 12/13/14 →
  T07/T11/T14; 15/23/24/25 → T14–16; 21/22 → T05/T09/T15 и явный запрет
  операторского accept. Все T — **план проверок, NOT_RUN**, не новое evidence PASS.

| Финансовые документы | Какие корректировки счёта/налога/подписанных документов нужны для изменения, доплаты/возврата; исходники сохраняются. DG-11/12, R7.6. |
| Техническое сопоставление | Существующие schemas/API/БД, version/hold/allocation/legacy upgrade-path, stock authority R2 и применимые поля политики. Текущий 30 мин резерв/старые обязательства не менять массово ради новых сроков. R4.1.2–3 не закрыты таблицей. |
| Операционный запуск | Источник актуальных отметок праздников, заполнение timezone/графика, реальные notification каналы и очередь/смены оператора. Согласованы интервалы и права, но доставка уведомлений/штат не доказаны. R5.3/4/R8. |

Независимую подготовку контрактов можно выполнять до внешних ответов, но зависимый
платёжный/документальный сценарий не считается принятым без них. Эта документационная
задача не разрешает автоматически начать код, deploy, рабочие миграции или все R4.

Личный/организационный buyer context24А отделён от плательщика. Подзаказы продавцов

## Единый процесс B2C и границы исполнения от30.10

Основание: [принятые решения](../UNIFIED_SPEC_MARKET_REQUIREMENTS_2026-10-29.md#b2c-decisions-20261030),
§6–11/14/18/30 ТЗ и R7.1.1/2. Это описание для исполнения существующего roadmap,
не второй backlog. Срез кода `2c6eed0`, анализ статический. Реализация полного B2C
не принята; перечисление переходов не объявляет новые endpoint или enum существующими.

Заказ, платёж, доставка, получение, документ и обращение имеют отдельные состояния.
Покупатель — личный аккаунт; получатель и плательщик не приобретают его права.
Несколько продавцов означают независимые подзаказы и платежи, не атомарную оплату
всей корзины. Переход всегда проверяется сервером по актуальным правам и версии.

### Первый пакет R7.1.1 — личная корзина с серверным владельцем и интерфейсом

**Предлагаемая граница исполнения:** вошедший пользователь без организации может
из общего каталога собрать, изменить и повторно открыть свою личную корзину,
увидеть актуальные условия и явно принять их изменения. Гость по-прежнему только
просматривает каталог. Пакет не создаёт заказ, платёж, резерв или отправление;
полный R7.1.1 остаётся OPEN. Продолжение в checkout требует отдельного связанного
пакета с контактами/получателем и необходимыми provider capability.

Это ограниченная самостоятельная вертикаль, а не backend без UI. На странице
должно быть понятно, что можно собрать корзину, но оформление ещё недоступно;
она не ведёт пользователя в организационный checkout и не имитирует успешный заказ.
Окончательный UI следует DESIGN_SYSTEM и двум JSON-контрактам перед реализацией.

**Почему первым:** сейчас Cart/Checkout/SupplierOrder/PaymentIntent привязаны к
buyerOrganizationId, assertBuyerAccess требует организацию, sessionApiContext
вызывает requireOrganizationMode. В apps/web текущая корзина использует workspace
организации и после checkout ведёт на `/clinic/orders`. Снятие только клиентского
guard не даёт безопасного B2C. Полезные quantity/version/acceptance механизмы и
общий каталог уже есть; их следует переиспользовать без снятия server permissions.

**Контракт до миграции:** личный owner выводится из проверенной серверной сессии,
не из body/header/sessionStorage. Личная и организационная принадлежность различимы
и не подменяют друг друга. Выбрать совместимую модель Cart: либо отдельная связь
личного владельца с ограничениями, либо отдельная personal aggregate с общими
чистыми правилами расчёта. Выбор фиксируется после анализа callers и миграции;
не делать все buyerOrganizationId nullable во всём commerce и не создавать
фиктивную организацию. Checkout/Order/PaymentIntent этим пакетом не мигрируются.
В PERSONAL не применять закрытые цены/договоры организации из активного membership.
Новая цена/stock/акция до принятия показывается как diff, не как скрытая замена.

**API-проект, не существующие маршруты:** личные list/current/create/item-change/
remove/validate/reprice операции с version и idempotency по применимости; owner
серверный. Старые организационные routes сохраняются. Точные paths/error codes и
политика current-cart фиксируются в общих схемах до backend. Прямое обращение к
организационному checkout с personal cart должно быть отвергнуто сервером.

| --- | --- |
| Схемы | `packages/schemas/src/index.ts`, `core-api.ts`, cart-correction tests; новую personal schema вынести в отдельный модуль с exports, не дублировать DTO в UI |

**Последовательность:** schema/owner/errors → миграция и personal сервис → focused
tests happy/denial/rollback до зависимого UI → client → каталог/личная корзина →
приёмка всего пути. Нужны два личных аккаунта A/B, пользователь с двумя ЮЛ,
аккаунт без membership, отозванная сессия и реальные изолированные cart fixtures.
UI обязан поддержать empty/loading/error/retry, черновик количества и conflict;
смена контекста или аккаунта не переносит чужую корзину/запрос.

**Критерий остановки пакета:** A без клиники сохраняет корзину после reload;
B не читает/меняет её по прямому ID; пользователь в личном режиме не получает
условия ЮЛ; concurrent/stale/replay не дублируют запись и не теряют количество;
quantity/price/UOM/rounding согласованы; stock не резервируется; старая корзина ЮЛ
и checkout работают по прежнему контракту; personal checkout отвергнут. Доказаны
server/API/UI, доступ с клавиатуры и RU/KK/узкий экран, без ложного order/live PASS.

При расхождении целевое поведение задают разделы29–30.10 выше;
прежние решения не переопределяют новые требования.

Обновлено: 08.10.2026. Связи R2/R4/R5/R7
[roadmap](../MAIN_ROADMAP_TO_PRODUCTION_2026-10-06.md).

### Процесс

Клиника собирает корзину нескольких поставщиков. Checkout проверяет актуальные
цену, остаток, акцию и договорную границу и создаёт отдельные supplier orders.
Состав/сумма версионируются; существенное изменение подтверждает клиника.
Далее идут подтверждение, оплата, отгрузка, получение, документы и возможный возврат.

Клиника видит расхождения и причину отказа; поставщик — состав, срок и доступные
действия; оператор — исключения. Чат не заменяет формальное согласование.
Нужны loading/empty/error/retry, защита дубля и понятный следующий шаг.

### Инварианты и существующая основа

#### Таймауты этапов — рабочая схема, не утверждённая для production

| Этап | Срок | Ответственная сторона |
| --- | --- | --- |
| Подтверждение наличия | 30 минут | Поставщик |
| Оплата и предоставление квитанции | 30 минут | Клиника |
| Полная сборка заказа | 1 час | Поставщик |

Уточнение владельца08.10: сроки и отсчёт пока рабочая схема, не окончательное
production-правило. Оплата отсчитывается после подтверждения заказа и доступного
счёта; сборка — после подтверждения полной оплаты. Для подтверждения наличия
последующее уточнение заменяет старт от поступления заказа: отсчёт предлагается
с первого открытия конкретного нового заказа сотрудником поставщика.

Если заказ пришёл вне расписания поставщика, уведомить стороны и объяснить
клинике, что он передан и будет обработан в ближайшее рабочее время. Не обещать
«завтра» автоматически при выходных. Начало рабочего дня, login или наличие
сохранённой сессии сами по себе не запускают этот таймер. Повторное открытие
не должно обнулять отсчёт. Нужны серверный факт открытия и согласованные роли.

Открытые вопросы: что делать с заказом, который вообще не открыли (иначе ожидание
не ограничено); запускать ли отсчёт при открытии вне расписания; приостанавливать
ли начатые таймеры на ночь/выходные; учитывать ли часы клиники для её оплаты.
Начало ожидания открытия и начало30 минут подтверждения — разные события.
По итоговому ответу08.10 все вопросы ожидания неоткрытого заказа, отсчёта вне
расписания, пауз, дальнейшего действия после напоминания и очерёдности/повторов
оповещений имеют статус **ОБСУЖДАЕМ С ПАРТНЁРАМИ**. Рабочая схема не стала
утверждённым production-регламентом.

При просрочке обязательно напоминание стороне, задерживающей этап, в кабинете
и оповещение по контактам организации. Для клиники — официальный публичный
и один резервный контакт; для поставщика — официальный публичный и два резервных.
Предусмотреть операторский звонок и выбранные для пилота SMS/email; WhatsApp
пока не включён. Конкретные провайдеры, порядок/частота каналов и подтверждения доставки
сообщений ещё не выбраны; наличие телефона не означает работающую интеграцию.

Действие после напоминания — **ОБСУЖДАЕМ С ПАРТНЁРАМИ**. Дополнительные15 минут
приведены как пример, не утверждённый срок. Автоотмена/блокировка не согласованы.
Уточнить начало отсчёта каждого этапа, рабочее/календарное время, выходные,
частичное подтверждение и сбои оплаты. Срок сборки не является сроком доставки.

Новые бизнес-сроки ещё не реализованы этим документом. Текущий30-минутный резерв
от checkout и15/30/60 эскалации проверки платежа ниже — другие механизмы.
Перед реализацией связать их с этапами/счётом/подтверждением денег: одинаковое
число30 не доказывает совместимость таймеров. Просрочка напоминания сама по себе
не разрешает освобождение резерва при заявленном переводе.

Локальный checkout-резерв —30 минут. Первое заявление об оплате после срока
блокируется; заявленный перевод удерживает резерв на проверку. Эскалация15/30/60
рабочих минут зависит от политики/фонового процесса.
Подтверждение полной ручной оплаты потребляет локальный резерв до отгрузки.
С внешним ERP-резервом необходим согласованный lifecycle, не перенос этой
семантики по предположению.

Частичные подтверждения/отгрузки/получения не превышают согласованное количество.
Получение подтверждает клиника. Отмена после оплаты, возврат товара и возврат денег
различаются. Повторная закупка создаёт корзину с текущими условиями.
Подарки/возвраты учитываются без молчаливого ухудшения согласованного предложения.
