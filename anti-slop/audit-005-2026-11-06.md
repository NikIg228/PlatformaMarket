## Находки

### 1. HIGH — карточки длинного списка сжимались и перекрывали соседние строки — FIXED LOCAL

R-03/R-35: адаптивная вёрстка должна сохранять читаемость содержимого.
При 55 обращениях в fixture первые 50 отображаемых карточек сжимались до 44px,
а нижняя граница содержимого доходила примерно до 74px относительно верха карточки.
Дефект воспроизвёлся на всех восьми дополнительных размерах окна, включая desktop.

Причина: неограниченные implicit grid rows в `.rows` внутри сжимаемой flex-колонки.
В `apps/web/app/workspaces/support.module.css` добавлен `grid-auto-rows: max-content`.
Токены, размеры controls, API и бизнес-логика не изменены. Теперь измеренная высота
карточки 110.8px, нижняя граница содержимого 93.8px; список прокручивается.
Добавлены два постоянных browser regression-сценария в `support-workspace.spec.ts`:
содержимое каждой строки помещается внутри неё, последнее обращение достижимо
и открывается. Это проверка наблюдаемого поведения, а не значения CSS.

[Мобильный список после исправления](../output/support-layout-audit-20261106/dense-list-mobile-fixed.png).

### 2. HIGH — ошибка списка на desktop превращается в вертикальную строку букв — FIXED LOCAL, follow-up

R-03/R-35: component должен перестраиваться по доступному месту, текст должен
оставаться читаемым. На desktop колонка списка имеет ширину 304px (280px на
промежуточной ширине), но общий feedback оставляет кнопку справа от текста.
Кнопка занимает почти всё доступное место; сообщение переносится по одной букве
и растягивает блок далеко вниз. На телефоне viewport media query переносит action
и поэтому тот же дефект не проявляется таким образом.

Места: `apps/web/app/workspaces/support.tsx`, list.error → inline ErrorState;
`packages/ui/src/styles/controls.css`, `.dm-notice` и viewport-only reflow `.dm-feedback`.
Это реальный дефект, хотя проверки отсутствия горизонтального overflow и
доступности кнопки через scroll прошли. Именно screenshot выявил нечитаемость.

[Ошибка списка на desktop](../output/support-layout-audit-20261106/list-error-desktop.png).
Нужен поддерживаемый общий вариант для узкого контейнера либо подходящая композиция
существующих adapters. Локальный override shared control не добавлялся.

### 3. MEDIUM — повреждённое изображение оставляет пустую модалку — FIXED LOCAL, follow-up

R-35 и Human: ошибка должна объяснять состояние в текущем контексте и иметь
доступный путь восстановления. После открытия повреждённого PNG видны имя файла
и кнопки закрытия, но объяснение не остаётся в модалке. Воспроизведено RU/KK,
1440px и 390px с touch/mobile emulation.

Причина: `packages/ui/src/support-files.tsx`, ветка `previewFailed`, использует
`ActionFeedback`. При наличии ToastProvider этот adapter публикует временный toast
и возвращает null. Поэтому ошибка не является содержимым открытого диалога и
после исчезновения уведомления остаётся пустое окно. Проверка ожидаемого alert
внутри dialog закономерно FAIL во всех четырёх профилях. Её не ослабляли до PASS.

[Повреждённое изображение на телефоне](../output/support-layout-audit-20261106/broken-preview-mobile.png).
Нужно постоянное состояние ошибки внутри диалога через существующий shared adapter;
общую политику toast для остальных consumers менять не требуется.

### 4. MEDIUM — неполная KK-локализация общих элементов — FIXED LOCAL, follow-up

В кабинете клиники над поддержкой остаются «Покупатель» и русская поясняющая строка.
Тексты самой поддержки переведены; пользовательские темы и сообщения не переводятся
автоматически и не считаются дефектом локализации.
[Кабинет клиники KK](../output/support-layout-audit-20261106/clinic-kk-files.png).
Это общий BuyerContextBar, а не новый дефект из-за изменения grid rows.
Кроме того, при ошибке файла заголовок общего toast остаётся «Ошибка», хотя
его описание уже казахское. [KK-уведомление](../output/support-layout-audit-20261106/kk-error-toast.png).
Это отдельная граница общего feedback, которую нельзя считать полностью
локализованной только по переводам формы поддержки.

### 5. MEDIUM — длинная переписка открывается на первых сообщениях — FIXED LOCAL, follow-up

При загрузке обращения с 12 длинными сообщениями история остаётся на `scrollTop=0`,
показывая первые сообщения вместо последних. Постоянный тест
`support background refresh preserves scroll and offers a new-message jump`
дважды воспроизвёл сбой на первоначальном ожидании прокрутки; второй запуск был
отдельным, после завершения сборки и остальных матриц. Повторять без новой
гипотезы не стали. [История после открытия](../output/support-layout-audit-20261106/history-start.png).

Место для исправления: `apps/web/app/workspaces/support-ticket.tsx`, эффект
первоначального заполнения `messages` и последующий `requestAnimationFrame`.
Гипотеза: прокрутка выполняется до окончательного commit/layout новых сообщений;
точная причина ещё не доказана. Сбой наблюдаемого поведения подтверждён.
Часть этого теста про приход следующего сообщения после прокрутки вверх не
достигнута, поэтому именно этот сценарий нельзя считать PASS текущего запуска.

## Проверки и ограничения

- Edge gate: попытка 1 — FAIL 8/8 на реальном перекрытии карточек; после исправления
  попытка 2 — PASS 8/8.
- State matrix: попытка 1 — 16 PASS / 8 FAIL из-за неточного KK-текста и неоднозначного
  combobox клиники. Попытка 2 после исправления locators и CSS — 22 PASS / 2 FAIL:
  Next.js dev indicator перекрывал центр submit. Проверка двух затронутых случаев
  после центрирования scroll и Playwright actionability — попытка 3, PASS 2/2.
  Это подтверждает перечисленные geometry assertions, но не закрывает находки №2–3.
- Дополнительная transient matrix: первые две попытки выявили ошибки scope locators
  для portalled toast. Третья дошла до preview и дала FAIL 4/4 на отсутствии ошибки
  внутри dialog. Лимит попыток достигнут, дальнейшего rerun этого gate не было.
- Финальная isolated go_live сборка unified web со встроенной TypeScript-проверкой:
  PASS, exit0. E2E typecheck: PASS, exit0. Использован штатный build через уже
  проверенный adapter с отдельным distDir/tsconfig; dev не останавливался,
  generated next-env восстановлен. Scoped E2E lint и diff hygiene: PASS.
- Штатная suite: первая попытка 25 PASS / 2 FAIL из 27. После завершения параллельной
  сборки повторены только два failed сценария без изменения тестов/исходников:
  attachments supplier PASS, initial history scroll снова FAIL. Итого 26/27
  сценариев имеют актуальный PASS; suite целиком **не зелёная**. Первый сбой toast
  не объявляется исправленным дефектом или доказанной проблемой нагрузки.

Команды: `npm exec -- playwright test --config=.tmp/support-layout-audit-20261106/{playwright,edges,transient}.config.ts`
(каждый config запускался отдельно; matrix attempt3 — только два failed cases);
`npm exec -- playwright test --config=apps/e2e/playwright.support.config.ts`
и targeted повтор с `--grep 'background refresh preserves scroll|attachments supplier: first ticket'`;
`npm run typecheck --workspace=@marketplace/e2e`;
`npm exec -- eslint apps/e2e/tests/support-workspace.spec.ts --max-warnings=0`;

Все записи/файлы в автоматизированных сценариях перехватывались fixture API;
рабочие обращения, сообщения и БД не менялись. Это Chromium, включая mobile/touch
emulation; физические Android/iPhone, их экранные клавиатуры, Safari/WebKit,
реальный screen reader и реальные upload/scanner endpoints не сертифицированы.
